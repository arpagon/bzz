# bzz v0.8.0 — Clipboard-first attachments

**Status:** Implemented locally 2026-08-21; release validation/manual desktop review pending.

## Goal

Make attaching a file, copied image, or screenshot feel immediate in the
composer: an explicit paste adds it to the draft, shows bounded progress, and
keeps it under the existing staged-upload and human-send boundary.

The user-facing model is:

- `Ctrl-v` explicitly reads/pastes once. A native file list becomes pending
  attachments; a native bitmap becomes one sanitized PNG attachment; otherwise
  bounded plain text is inserted at the composer cursor.
- `Delete` removes the most recent draft attachment. A visible attachment list
  makes this unambiguous.
- `Ctrl-c` clears the draft through the existing explicit confirmation, which
  removes text and draft attachments but never sends anything.
- An explicit local-path fallback remains available for terminals/desktops
  without usable native clipboard file data. Its final shortcut and label will
  be selected after the interaction prototype; it must not masquerade as a
  clipboard paste.

The current `Ctrl-a` path prompt is a transitional behavior, not the v0.8
primary flow. The new composer header and generated help will describe the
actual effective bindings.

## Clean-room boundary

Concord is behavior-only research: it demonstrates a useful model of an
explicit clipboard paste that can produce files, an image, or text, plus
separate clearing and removal operations. bzz will not copy its source,
assets, strings, configuration grammar, test cases, or platform integration.
The bzz architecture, input names, copy, tests, and visual fixtures are
independently authored.

## Product decisions

### Explicit clipboard ownership

Clipboard reads happen only after the user invokes the paste action while a
publishable composer owns input. bzz will never poll, monitor, log, index, or
sync clipboard contents. Existing `ui.clipboard` continues to govern explicit
OSC-52 *writes*; v0.8 introduces a separate strict media setting for explicit
clipboard *reads*, defaulting to enabled and allowing an owner to disable it.

A clipboard read has deterministic precedence:

1. a validated native file list;
2. a native bitmap;
3. bounded plain text;
4. a clear, content-free unavailable/unsupported status.

This avoids accidentally inserting a copied filesystem path as a message when
that path represents an attachable regular file. It also lets ordinary copied
text retain normal composer behavior.

### Attachment lifecycle

Every accepted clipboard file/bitmap enters the existing `DraftAttachment`
lifecycle before network access: validate, privately stage, sanitize image
bytes where applicable, then upload asynchronously to the active community.
The composer renders pending, ready, and failed state above the text input.

Removing an attachment or confirming clear cancels/invalidates its local
upload generation, removes pending staged bytes, and prevents a late worker
result from restoring it to the draft. An already uploaded unreferenced blob
may remain on the relay because the protocol has no safe ownership-scoped
delete contract; it is never referenced in a message after removal.

### Compatibility and fallback

Native clipboard integration is optional at runtime. On unsupported systems or
when clipboard file formats are absent, bzz must remain usable through its
explicit local-path flow and terminal bracketed text paste. No shell command,
file chooser, browser, helper daemon, or ambient clipboard polling is used.

The release notes will call out the precise migration from the pre-v0.8
`Ctrl-a` path prompt. Keymap overrides remain owner-controlled and fail closed;
new composer actions cannot be bound in a workspace, Inbox, or overlay scope.

## Scope

### 1. Typed composer intent and presentation

- Add typed, composer-only intents for paste/import, remove-last-attachment,
  and the existing clear action; update the generated keymap help and narrow
  composer title without hard-coded terminal-family assumptions.
- Render a compact, measured attachment queue with sanitized filename, safe
  size, state, and an error/retry affordance. It must work with graphics off
  and never use inline previews as the only indication of an attachment.
- Preserve UTF-8 cursor behavior, mention completion, drafts, `Esc` close,
  and the explicit `Enter` send boundary. Paste text must go through the same
  bounded composer insertion and mention invalidation rules as typed text.
- Retain existing direct local-path attachment as a clearly named fallback
  during the transition; decide its long-term binding after prototype review.

### 2. Clipboard adapter boundary

- Define a small async/background clipboard-import interface with a production
  platform implementation and deterministic fake implementation for tests.
  The UI thread receives only a typed, bounded result; it never handles raw
  platform clipboard objects.
- Audit and pin any new clipboard dependency before adoption. It must support
  the target Linux clipboard environments without invoking a shell, preserve
  release/debug isolation, and degrade cleanly when unavailable.
- Recognize only a native file-list representation, a decoded bitmap, or
  plain UTF-8 text. Reject unknown/custom clipboard formats, malformed
  paths/URIs, control-bearing text beyond the composer sanitizer's contract,
  and sources exceeding an early bounded read allocation.
- Add terminal bracketed-paste routing for text/path fallback without treating
  untrusted pasted strings as executable commands or filesystem authority.

### 3. Safe file and bitmap staging

- For each candidate file, use the existing regular-file/non-symlink and
  staged-copy checks, revalidate after opening, enforce per-file and aggregate
  limits, and never persist or display the source path. Canonical staging names
  remain content-addressed and owner-private.
- Bound native bitmap dimensions and allocation before PNG encoding; encode it
  through bzz's existing safe image sanitation path so metadata and unsafe
  formats do not enter the draft.
- Preserve the current limits (eight outbound attachments, image/file/video
  ceilings, decoding limits, staging privacy, upload auth, relay-origin
  checks, and acknowledgement handling). No clipboard input bypasses NIP-92
  descriptor verification.
- Partition in-flight work by active community, identity, composer target, and
  generation. Switching target/community, locking, closing the composer,
  removal, or clear must make stale completions harmless.

### 4. Draft persistence, recovery, and cleanup

- Persist only the existing sanitized draft body, validated attachment
  descriptors/pending staging metadata, and mention metadata. Never persist a
  clipboard payload, source URI/path, native format identifier, or clipboard
  error containing those values.
- On restart, resume only valid pending staged uploads in the matching active
  scope; repair missing/stale staging safely. A clipboard import interrupted
  before staging creates no draft attachment.
- Make clear/remove behavior idempotent across a background completion race;
  verify no removed item reappears and no abandoned pending staging file is
  retained solely by an invalid draft reference.

### 5. Documentation and release evidence

- Update configuration, media, keymap, manual-E2E, troubleshooting, and release
  notes with bzz-owned wording: paste precedence, privacy switch, fallback,
  sizes, clear/remove semantics, and platform limitations.
- Add an ADR covering explicit clipboard privacy, supported import classes,
  dependency choice, no-shell boundary, and stale-upload generation policy.
- Validate release builds on a real Ghostty session and at least one
  non-graphics terminal. Use disposable generated images/files and no user
  clipboard contents in committed fixtures, logs, or screenshots.

## Milestones

1. **Design and safety contract** — ADR, typed actions/keymap model, strict
   configuration, dependency audit, fake clipboard interface, and threat-model
   tests. No platform clipboard access yet.
2. **Composer queue** — measured pending/ready/failed attachment presentation,
   clear/remove/retry lifecycle, draft persistence, and stale-generation tests
   using a fake importer.
3. **File-list import** — explicit native file-list import into existing secure
   staging/upload machinery; validate limit, symlink, target-switch, and
   late-result behavior with a fake relay.
4. **Image and text import** — bounded clipboard bitmap conversion plus text
   and terminal-paste routing; test precedence, UTF-8 cursor behavior,
   sanitization, and unavailable backends.
5. **Hardening and release** — manual cross-terminal journey, locked/offline
   regression suite, benchmarks for bounded import work, documentation,
   release-binary smoke, and a review of the legacy path prompt's final status.

## Acceptance criteria

1. From an open composer, one explicit paste can attach copied regular files or
   a copied image, or insert ordinary copied text, without requiring a source
   path to be typed and without publishing a message.
2. Clipboard data is never read before that explicit action, never logged or
   stored raw, and can be disabled independently of OSC-52 clipboard writes.
3. Every attachment follows the existing private staging, validation,
   sanitization, authenticated upload, and acknowledged-send path; malformed,
   oversize, special, symlinked, cross-scope, or stale input cannot reach the
   relay or survive as a draft attachment.
4. Clear/remove/retry/close/target switch are race-safe: no stale upload can
   resurrect a removed attachment, and the visible queue always agrees with the
   persisted draft.
5. Graphics protocol, media autoload, Inbox/read state, identity/profile
   isolation, locked mode, dependency pins, terminal restoration, and the
   draft-only Codex/human-send boundary are unchanged.
6. Release evidence includes deterministic unit/integration tests, strict
   Clippy, real release builds, and a manual Ghostty plus non-graphics-terminal
   review using disposable content only.
