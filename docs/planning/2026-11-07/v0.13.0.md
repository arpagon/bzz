# bzz v0.13.0 — Current Buzz protocol baseline

**Status:** Proposed 2026-11-07. Scope decisions D1–D4 answered the same day.
Revised to bring every previously deferred upstream surface into this release.

**Prerequisite:** publish v0.12.0 and then v0.12.1 (validated 2026-08-28,
untagged) after their pending production acceptance. Only then tag v0.13.0.

**Protocol baseline:** move from `block/buzz`
`9f55bf67456be10ff7c8238bf0d9e12e582848f6` (2026-08-24) to
`1bb2ad443d4ee4512dd0927888ad21a4a1c041bc` (2026-11-06) or a later reviewed
`main` commit. The final revision is fixed in M0 and must not move after that.

## Release thesis

bzz's pin is 878 upstream commits old. v0.13.0 makes bzz a complete client of
current Buzz:

- correct against today's relay: channel types, roles, membership, NIP-OA time
  bounds, mention validation and search limits;
- able to join communities that require federated identity (NIP-FI), through
  its own NIP-FA browser sign-in or through a running Buzz Desktop;
- feature parity for the user-facing surfaces upstream added: system
  channels, artifacts, custom emoji, presence and status, NIP-CW channel and
  thread windows, huddles with audio, reporting and send-to-channel; and
- a local agent broker, so agents the user runs can act through bzz without
  holding their own secret key or relay connection.

This is by far the largest bzz release. It changes three things earlier
releases kept fixed, and each change gets its own ADR before implementation:

1. **Key custody.** bzz will hold agent keys for the broker.
2. **Credentials.** bzz will hold an adapter session and agent grants for NIP-FA.
3. **Media.** huddles add microphone capture, audio playback and a native
   Opus dependency.

The explicit human send boundary stays as it is. bzz still never publishes on
the human's behalf without an explicit action. Broker actions are signed only
with agent keys, under per-action policy.

## Cross-cutting rules

1. **Capability first.** Every optional relay surface is discovered from NIP-11
   on the configured relay origin. If it is absent, bzz keeps its current
   behavior and shows no notice.
2. **Proof before trust.** Relay-signed snapshots, bounds and lifecycle events
   are checked for signature, pinned signer, community, viewer, scope and
   bounds. Any mismatch means "cannot prove" and falls back.
3. **Untrusted text stays inert.** Titles, labels, shortcodes, statuses and
   artifact payloads go through the existing sanitizer and never authorize an
   action.
4. **Privacy.** No assertions, session tokens, grants, handoff secrets, NIP-98
   proofs, audio, labels, titles, statuses or identifiers enter logs,
   diagnostics, telemetry or snapshots. New diagnostics are fixed enums and
   bounded buckets only.
5. **Admission budget.** Every new subscription and publication goes through the
   v0.12.1 scheduler and priorities. The broker and huddles get their own
   priority classes below interactive human work.
6. **No silent republish.** The outbox's acknowledgement rules apply to every
   new event type.
7. **Each milestone has its own exit gate** and lands behind its own tests. The
   release is not tagged until all of them pass.

## M1 — Channels, roles and correctness

1. Parse and store the new 39000 tags: type, creator, labels, `join_role`,
   unlisted. Use a migration with nullable columns.
2. **System channels (D4):** request them with the NIP-CL opt-in
   (`#t:["system"]`). Show them in a collapsed `System` sidebar group. They are
   read-only for every role in v0.13.0, because writing into an agent's config
   channel can break it. Unknown future types stay read-only in the same way.
3. Read the viewer's role from 39002. `guest` gets a read-only composer with a
   fixed one-line notice. The relay stays the authority.
4. Unlisted channels the viewer has not joined stay out of browse and finder.
   They can still be opened from a link.
5. Membership notices add and remove channels live: auto-join, delete, kick,
   moderation DM. A removed selected channel keeps its draft and moves the
   selection somewhere safe.
6. Map the SDK's malformed-mention error to a composer error that keeps the
   draft.
7. Verify NIP-OA with `verify_auth_tag_for_auth_event` or the same `created_at`
   bounds. Add fixtures for expired and not-yet-valid tags.
8. Require 3 characters for message prefix search and show a fixed hint below
   that. The relay applies the minimum to every lexeme of the last
   whitespace-separated word, after Postgres' `simple` parser splits on
   punctuation. `bzz-dm-x` therefore yields no hits because `dm` is too short.
   The client check must use the same rule. Update profile-search expectations for `name`/`display_name` and
   verified names.

**Exit:** fixtures for every type and role render correctly, and membership
changes apply without a resync.

## M3 — Federated identity (NIP-FI, NIP-FA, local provider)

### Configuration and discovery

- Read `limitation.federated_identity` and the host-specific `requires_nip_fi`
  from NIP-11.
- NIP-FA leaves adapter discovery out of scope, so each community gets an
  optional `identity_adapter` URL in config (HTTPS only, loopback allowed for
  testing).
- A community that requires FI but has no adapter or provider configured gets a
  terminal state with setup instructions, and never a reconnect loop.

### NIP-FA browser sign-in

1. Generate a handoff secret and listen on `127.0.0.1` or `[::1]`, any port.
2. Open `/v1/login/start` with the S256 challenge. If no browser can be
   opened, show the URL instead.
3. Exchange the code with an HTTP client that follows no redirects, then call
   `/v1/session`. Reject the login when the two `expires_at` values differ as
   instants.
4. Store the session token encrypted, in the same keychain or encrypted-file
   backend as the identity, scoped to adapter origin and identity. It is never
   sent to any other origin.
5. Do not publish `profile_projection` unless the operator has explicitly opted
   in.

### Assertions and transport

1. Get assertions from `/v1/identity/assertions` with the session plus a fresh
   NIP-98 proof over the exact body. Send the canonical `wss://host[:port]`
   form. Reject a response whose `nostr_pubkey` differs.
2. Send `Nostr-Federated-Identity: Bearer …` on the WebSocket upgrade, on every
   NIP-98 route (`/query`, `/events`, `/count`) and on every Blossom route
   (`/upload`, `/media/upload`, `/media/*`). Fetch evidence first, then sign
   the proof just before sending. Follow no redirects on relay traffic.
3. Re-mint the assertion before it expires. Treat a relay close at the
   session deadline as a normal reconnect with fresh evidence, not an error.
   The new socket goes through the v0.12.1 admission pacing.
4. Handle the denial tables exactly as NIP-FA says:
   - `session_required` or `session_expired`: clear the session and ask for
     sign-in again.
   - `authorization_denied`, `invalid_proof` or `binding_mismatch`: keep the
     session, show the refusal and do not retry.
   - 429, 5xx or a network failure: back off within a bound, honoring
     `Retry-After`.
   - An undefined code: treat it as a refusal.
5. Relay denials: a 401 with `WWW-Authenticate: Nostr`, a 403
   `evidence rejected` or a 1008 policy close after AUTH map to typed
   community states. Raw text is never stored.

### Buzz Desktop provider

Implement the caller side of `docs/local-credential-provider.md`:

- discovery in the spec's order;
- one token per identity, bound relays compared after normalization;
- public key, NIP-44, NIP-OA tag and `federated_identity` evidence;
- remote signing of complete unsigned events.

It becomes a new identity type, `buzz-desktop`, in which bzz holds no secret
key. Version 1 of the spec has no Windows transport, so on Windows this
identity type is unavailable and the UI says so.

### Verified profiles

Read kind 30382 from the pinned relay signer and show a verified marker on
names, in the mention picker and on profile cards. Never show raw claims.

**Exit:** against a fake adapter and an FI-enforcing pinned relay, sign-in,
evidence on every route, deadline reconnect, every denial code and the Desktop
provider all pass. No credential appears in any output.

## M4 — Channel artifacts (NIP-AR)

1. Read `artifacts` from NIP-11 (`sync`, `modes`).
2. Use the sync subscription per selected channel, current-state queries across
   readable channels and incremental reads. Keep the held list within
   `max_events`.
3. Store only current state locally, plus the IDs needed for `prev`. Revisions
   never count as chat messages, unread or mentions.
4. UI: an artifacts panel per channel and thread, and a cross-channel "My
   tasks" view filtered by `assignee`.
   - Known types `buzz.task` and `buzz.project` get structured rendering.
   - Every other type shows a safe fallback: title, type and home link.
5. Editing: create, update, delete and restore for `buzz.task` and
   `buzz.project`.
   - Keep unknown fields and annotation tags, or decline the edit.
   - On `conflict`, reload the head, reapply the change, and tell the user if
     that is impossible. Never resubmit with only `prev` replaced.
6. Move asks for confirmation and shows the destination audience and what will
   be shared, as the spec requires.
7. Match upstream's `buzz.task` and `buzz.project` content schemas exactly by
   reading the Buzz app sources in M0. If they are not published, the types are
   read-only in bzz.

**Exit:** create, conflict, move, delete, restore and redaction fixtures pass,
and no artifact changes chat counters.

## M5 — Custom emoji (NIP-CE, NIP-30)

1. Render `:shortcode:` from message and reaction `emoji` tags. Any lookup
   happens only after the history is drawn.
2. Resolve unknown shortcodes with exact `#d` lookups, at most 50 per filter,
   batched through the admission scheduler. Apply the newest-wins rule across
   authors with the relay's tie-break.
3. Graphics terminals show the image through the existing avatar and media
   pipeline, fetched without credentials from `http(s)` URLs of at most 2048
   bytes. Other terminals show a styled `:shortcode:`.
4. The reaction picker gets custom emoji search through NIP-50 prefix mode on
   `POST /query` (at most 50 hits). Reacting with a custom emoji adds the
   `emoji` tag.
5. Also read the `kind:30030` set `buzz:custom-emoji`, preferring the newest
   event for a shortcode.

**Exit:** history renders without lookups, the fallback never breaks layout,
and image loading follows the media security rules.

## M7 — Channel and thread windows (NIP-CW)

Spec: `docs/nips/NIP-CW.md`, which governs, plus the frozen contract in
`docs/bridge-channel-window.md`.

### Channel windows (39006)

1. Page the selected channel timeline by top-level rows on `POST /query`:
   `top_level: true`, exactly one `#h`, `limit` as the row budget,
   `include_summaries` and `include_aux`. Use `until` and `before_id` together
   or neither. There is no timestamp-only cursor.
2. Split each response by kind before any cursor math:
   - rows;
   - the aux closure: reactions, deletions (5, 9005), edits (40003) and
     deletes of those;
   - 39005 summaries;
   - exactly one 39006 bounds event.
3. Verify the 39006 signature and pinned relay signer. Check that its `d`
   suffix (`head` or `<created_at>:<event_id>`) equals the cursor bzz sent, and
   reject it on mismatch. Paging uses only `has_more` and `next_cursor`, never
   row counts. `next_cursor = null` exactly when `has_more = false`.
4. Follow the frozen client obligations:
   - pages are immutable history chained cursor to cursor;
   - live events go in a separate overlay and are never spliced into pages;
   - reconnect refetches page 0 and re-arms live with `since: now`;
   - replies never enter the channel timeline.
5. **Local store:** pages are written to SQLite as verified events, so search,
   Inbox and offline reading keep working. 39005 and 39006 are never stored, as
   today. The window replaces the current HTTP composite-cursor gap repair
   only for the selected channel's visible history. Background channels keep
   the existing backfill.
6. The aux closure replaces per-message `#e` fan-out for reactions and edits on
   windowed pages. That removes frames from the admission budget.
7. A row with `depth = 1` and `broadcast = true` is a top-level row (the relay's
   predicate). Show it in the timeline with its thread reference.

### Thread windows (39007)

1. Use `thread_window: true` on `POST /query` when the relay advertises it.
2. Open a thread at its newest replies, page backwards with the exact composite
   cursor, and request reactions, edits and deletions in the same window.
3. Verify the relay-signed 39007 bounds against host, reader, channel, root,
   cursor, kinds, depth, limit and aux choice. Use only its `has_more`, never
   row counts.
4. Merge into the local archive without breaking the bounded retention of 500
   roots or the 39005 summary rules.

### Fallback

Without the capability, or on any rejected bounds event, keep the current
oldest-first thread path and the existing channel backfill. There is no
user-visible notice.

**Exit:**

- Channel and thread fixtures page across dense seconds and exact-multiple
  final pages without gaps or duplicates.
- Mismatched or forged bounds are rejected.
- Live events never enter page history.
- Reconnect refetches only page 0.
- Selecting a channel sends fewer frames than the current path.

## M9 — Local agent broker

bzz acts as a broker host under the `buzz-sdk::broker` contract.

1. **Transport:** loopback HTTP `POST /v1/action`. Each agent gets one bearer
   credential per agent identity, issued by bzz, shown once and revocable.
   Binding is on `127.0.0.1` only, and the endpoint is not served while bzz is
   locked.
2. **Keys:** bzz creates and stores agent keys in the existing keychain or
   encrypted-file backend, separate from the human identity.
   - Agents never receive the secret key.
   - The owner's NIP-OA tag is made once, with explicit confirmation.
3. **Actions:** `channel.read`, `message.post`, `message.reply`, `reaction.add`,
   `profile.set`, `storage.address`, `agents.create`, `agents.update` and
   `agents.delete`.
   - Requests are authenticated, authorized, validated and executed in that
     order.
   - Wire types are strict as the contract demands: no unknown members, no
     explicit `null`, canonical identities.
4. **Policy:** per agent and per action, set in a broker panel.
   - Destinations are limited to channels where the agent has the relay `bot`
     role.
   - Write actions are rate-limited at broker priority, below human work.
   - The owner can pause any agent with one key.
5. **NIP-FI:** for FI communities, get agent grants and agent assertions
   (NIP-FA agent keys). Handle `invalid_grant` by discarding the grant, and
   revoke through `/v1/nip-fi/agent-revoke` on agent deletion.
6. **Presence:** publish 20003 through M6.
7. **Visibility:** an activity log that is local, bounded and content-free, so
   the owner sees what each agent did. bzz still does not spawn agent
   processes. The user runs them and gives them the credential.

**Exit:** the upstream broker contract tests pass against bzz's host, policy
denials are typed, and no secret key or credential crosses the boundary in
either direction.

## M10 — Send to channel and report

1. **Render** `["buzz:sent-from-thread", root, excerpt]` messages with a
   sanitized "from thread" reference that opens the thread.
2. **Send to channel** from an open thread: kind 9 with that tag and no NIP-10
   tags. The excerpt follows desktop's `summarizeThreadRoot` clipping (by code
   point, words split by UTF-16 unit). The root must be a local thread root in

3. **Report** (NIP-56 kind 1984): a message or an author, one of the seven fixed

   because the relay keeps reports in the moderation queue only.

**Exit:** both go through the human send boundary and the outbox, with
fixtures for invalid roots and every reason.

## Explicit non-goals

v0.13.0 still does not:

- spawn or supervise agent processes, run models, or speak ACP;
- publish human presence or typing without the opt-in;
- implement relay, operator, admin, push, App Attest or deletion APIs;
- serve as a NIP-46 remote signer or expose the broker beyond loopback.

## Definition of done

1. Every milestone's exit gate passes on the fixed baseline with Rust 1.98.1.
2. bzz connects to FI-required communities through NIP-FA or Buzz Desktop, and
   fails clearly when neither is configured.
3. System, announce, unlisted and unknown channels behave as specified.
4. Artifacts, custom emoji, presence and status, channel and thread windows,
   huddles, send-to-channel and report work against the pinned relay.
5. The broker lets a local agent act through bzz with no secret key or
   credential crossing the boundary, under owner-visible policy.
6. No credential, assertion, audio or content leaks into logs, diagnostics,
   telemetry or artifacts.
7. The documentation lists exactly what is supported.
8. Every row of "Testing v0.13.0" is proven in `docs/validation-v0.13.0.md`
   with its command and result, or marked pending with the reason.
