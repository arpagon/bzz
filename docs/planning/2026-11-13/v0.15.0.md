# bzz v0.15.0 — Local agents

**Status:** Draft, 2026-11-13. The owner set the direction and answered the
decisions marked *decided* below. Six are *proposed* and wait for him
(P1–P6). Nothing here is implemented.

**Prerequisite:** v0.14.0 is published (2026-11-13, `80e1b07`).

**Baselines, fixed in M0:**

- Buzz: `block/buzz` `bf3bdd0eaefe39289bf9620594f254c7f68897f5`, the v0.14.0
  pin. It moves only if a milestone needs it.
- Pi Durable: `@earendil-works/pi-durable` 1.5.0, the version Buzz 1.0 pins.
  It moves when the Buzz pin does.
- Node 22.19 or newer on the owner's machine, for agents only. bzz without
  agents stays one binary.

## Release thesis

bzz has shown and talked to agents since v0.11, and since v0.13 it holds an
agent's key for a process the user runs himself. It has never run an agent.
v0.15.0 makes bzz **create and run agents on the owner's machine**, and lets
the owner **move** one to another machine.

An agent is three things, placed separately:

| Piece | Where it lives | Rule |
|---|---|---|
| Its **key** | in bzz | the model and its tools never see it |
| Its **memory and disk** | two SQLite files in the agent's folder | no machine-specific paths inside; a move is a copy |
| Its **hands** | wherever real programs run | granted by the owner, never by default |

Two words, kept apart, as Buzz does (`Local` or a provider on one agent
record, `block/buzz` `docs/remote-agents.md`):

- **Local agent:** this bzz holds its key and starts its process.
- **Remote agent:** something else does. On another machine that is Buzz's own
  `buzz-acp`, which already knows how to hold a key, talk to the relay and
  start an agent under it.

The bridge is one explicit act, **move**. Buzz 1.0 already uses "export" and
"import" for an agent's definition only (name, instructions, model, picture;
a new key on import), so bzz does not reuse those words.

## What was tried first

An experiment ran before this plan (`runs/experiments/agents/pi-durable-harness/`,
local and untracked: twelve reports and eight spikes). Everything below ran on
Linux x86_64 with Node 26.5 and disposable keys.

| Spike | What ran | Result |
|---|---|---|
| S1 | Buzz 1.0's own Pi host, unmodified, driven by a script; killed in the middle of a send | resumes in the next process; 32 s wait on a stale lock; the model sent twice; always gives the agent the user's real files and shell |
| S2 | a host of ours on Pi Durable, 89 lines, as a separate process | ready in 0.15 s; same mention twice maps to one submission; one reply with a rule on bzz's side, two without |
| S3 | a real mention on the pinned relay → host → bzz's v0.13 broker → reply; host killed after the publish | one reply on the relay with the rule, two without; no change to bzz needed |
| S8, S9 | the agent's disk in SQLite with a shell (just-bash) and git (isomorphic-git), no real process; Pi Durable's own environment suite | bzz's repository cloned in 7.1 s, 0 of 457 files differ from real git, real `git fsck` clean; push and pull work; 30 kills, 0 inconsistencies; 24 of 24 suite cases pass (7 fail with two planted faults); 1,044 lines of ours |
| S10 | the real `buzz-acp` from the pin starts our host over ACP | reply in 1.1 s; after `buzz-acp` is killed and restarted, a new ACP session lands in the same conversation; a mention `buzz-acp` hands over twice is answered once; `!shutdown` stops it in 0.3 s |
| S11 | a move: answer locally, stop, copy two files to another folder, continue under `buzz-acp` | the remote copy answers once and continues the same conversation; the file the agent made is on the moved disk |
| S12 | a real model (`openai-codex/gpt-6-luna`) through the owner's Pi login | answers through the tool, remembers, publishes once after a kill |

Costs found: 335 MB of memory to clone a 40 MB repository; git without
`rebase`, `stash`, conflict merges or SSH; command output arrives when a
command ends; 115 more npm packages for the shell and git; `buzz-acp` gives its
agent text, not fields. Not tried: macOS, Windows, Claude Code, Codex and Grok
under bzz, several conversations in one harness process, a token refresh, a
repository of hundreds of MB.

## Design

```text
Buzz relay ⇄ bzz (Rust)   relay session · agent keys · who may wake an agent ·
                │           inbox and reply ledger (SQLite) · process supervision · TUI
                │ ACP over stdio (one process per agent)
             harness       Pi Durable host (Node) │ Grok │ Codex │ Claude Code
                │ tools: only what bzz serves (send, read, react)
             agent folder   memory.sqlite · files.sqlite        ← what a move carries
```

1. **bzz decides and signs.** It delivers a mention or a DM to the agent when
   the author may wake it, and publishes what the agent sends through the
   tool. The agent holds no key and no relay connection.
2. **One final reply per mention, by construction.** When a final `send`
   arrives, bzz finds the mention from the calling session's live turn, never
   from the tool's arguments. It signs the reply, stores the signed event
   under the mention, then publishes. After a crash it publishes the stored
   event again; a relay that has it keeps one copy. A second final `send` for
   the same mention returns the stored reply and publishes nothing.
3. **A capability record per harness**, printed by `agent show` and at
   creation: what survives a restart, whether it has its own disk, whether a
   rule is enforced by the harness or only by bzz. A mode a harness cannot
   enforce is not offered.
4. **The Pi Durable agent's default world is its own disk**: a SQLite file
   reached only through the host, with a shell and git that start no real
   process, and a network allow-list. Real folders appear under `/mnt/<name>`
   only when the owner grants them, read-only unless he allows writes. Granted
   folders belong to the machine and do not move.
5. **A remote copy runs under `buzz-acp`.** There Buzz's rules apply: the key
   sits beside the agent and the agent posts with the `buzz` CLI.

## Decisions

Decided by the owner (2026-11-13):

| # | Decision |
|---|---|
| D1 | Agents need Node 22.19 or newer. bzz without agents stays one binary. |
| D2 | An agent lives while the TUI is open, and optionally as a background service. |
| D3 | Who may wake an agent is set per agent: the owner only by default; the owner can open it to listed people or to anyone. |
| D4 | The default is the agent's own sandbox and disk: simple, no Docker. Real folders are opt-in. Git is required in the default sandbox. |
| D5 | bzz writes its own Pi Durable host. Buzz's host is the reference, not a dependency. |
| D6 | "Mobile" means a cold move plus borrowed machines. The owner's GPU machine is local. Cloudflare is later, as one possible place for a remote agent. |
| D7 | Local and remote agents are separate concepts, joined by **move**. A moved agent stays a Pi Durable agent with its memory and disk. |
| D8 | For a remote copy, Buzz's rule is accepted: the key sits beside the agent. |
| D9 | Our host under `buzz-acp` reads Buzz's prompt text; a test at each Buzz pin guards it. |
| D10 | Move is part of v0.15.0. |
| D11 | The model comes from Pi's own configuration and login. bzz stores no provider keys. |
| D12 | One harness process per agent. |
| D13 | Adding an agent to a channel follows Buzz 1.0: the `bot` role only in Solo chats. |
| D14 | Four harnesses: Pi Durable, Grok, Codex and Claude Code. |

Proposed, waiting for the owner:

| # | Question | Proposal | Why it is open |
|---|---|---|---|
| P1 | How bzz drives the four harnesses | **One ACP client in bzz.** Pi Durable's host and Grok speak ACP themselves. Codex and Claude Code go through their official ACP adapters. Tools reach a harness as a small server bzz runs (`bzz agent-tools`), with a credential made per launch | Two reports disagree. The alternative is a native driver per harness, as Buzz 1.0 does: no adapters and no credential, but three protocols to follow, two of them undocumented or experimental |
| P2 | What v0.15.0 promises per harness | Pi Durable: everything in this plan. Grok: supported. Codex and Claude Code: **experimental**, behind a version range | None of the three has run under bzz |
| P3 | Claude Code's sign-in | bzz starts the owner's own `claude` program with whatever sign-in he made there, and says which one is in use | Anthropic forbids a product from offering claude.ai login; a user signing in to the unmodified program is allowed. Buzz 1.0 moved to API keys only on 2026-11-06 |
| P4 | Platforms | Pi Durable agents on Linux and macOS in v0.15.0, Windows when its tests pass. The three coding harnesses on Linux and macOS only | Claude Code and Grok have no sandbox on Windows; nothing was run off Linux |
| P5 | What bzz says about a coding harness | It runs a real shell as the owner's user, in a folder bzz makes plus folders the owner grants, with the harness's own sandbox on. bzz never gives it the key. bzz cannot promise the key is out of reach | True of every design; the owner should accept the wording |
| P6 | Where the cut is if the release grows too large | M0–M5 are v0.15.0. M6 ships with it if its gates pass by then, else in v0.15.1. M7 is v0.15.1 | The owner asked for all of it in one version |

## Cross-cutting rules

The nine rules of v0.13 and v0.14 still apply. Four are added:

10. **The key stays in bzz.** No agent key, owner key or relay credential is
    placed in a harness's environment, arguments, files or tool results, for
    any local agent.
11. **bzz enforces, the harness is not trusted to.** One reply per mention,
    who may wake, and what an agent may do are checked where bzz serves the
    tool or delivers the mention.
12. **Say what a harness cannot do.** Every capability a harness lacks has a
    stated fallback and appears in `agent show`.
13. **Pinned and without install scripts.** The Node packages of the host are
    installed from a lock file committed to bzz, with install scripts off.

## M1 — The agent runtime in bzz

- **Processes:** one group per agent, an environment built from nothing, an
  ownership record (pid, start time, boot id), a sweep of leftovers at
  startup, stop by TERM then KILL. The host exits when bzz does.
- **ACP client** over stdio: `initialize`, `session/new`, `session/prompt`,
  `session/cancel`, permission requests, updates. The place and the request
  travel as fields under a namespace of ours.
- **Inbox and reply ledger** in bzz's database (migration 18): a mention's
  state, and the signed reply stored before it is published.
- **Tools:** `send`, `read`, `react`, on the v0.13 broker. A credential per
  launch, held in memory, revoked at exit; each call bound to the caller's
  live turn.
- **Admission:** owner only, a list, or anyone, per agent (D3). DMs stay
  owner only, as the relay requires.
- **While a turn runs:** the agent's typing indicator; a failure reply in the
  thread when a turn fails; failures named by kind (limit reached, sign-in
  needed, provider error).
- **After a crash:** recover before restarting anything; continue a cut-off
  turn with a warning, at most three times in five minutes; never hand a
  mention again to a harness that cannot tell it has seen it.

**Exit:** on the pinned relay, a mention is answered once through a scripted
harness, with the harness killed before, during and after the publish.

## M2 — The Pi Durable host

- A Node program, one per agent: Pi Durable on `memory.sqlite`, an ACP face,
  one conversation per channel or thread, the mention's event id as the
  request id.
- Models from Pi's own login file and settings, read as Pi reads them (D11).
  Providers that come from a Pi extension need a Pi Durable entry in that
  package; `agent new` says so when the chosen model is not available.
- Installed on first use from the committed lock file.

**Exit:** S2, S3 and S12 as tests against bzz itself: resume after a kill, one
reply, memory across turns and restarts.

## M3 — The agent's disk

- `files.sqlite`: the filesystem of S8, with content in chunks named by hash.
- The shell and git with no real process; `git` covers the everyday commands
  and names what it lacks.
- Granted folders under `/mnt/<name>`, read-only by default.
- A network allow-list per agent; credentials for a private remote come from
  bzz at the moment of use and are never stored on the agent's disk.
- A checkpoint of both files when the agent is idle.

**Exit:** Pi Durable's environment suite passes on three platforms; a clone,
commit, push and pull against real git; thirty kills without inconsistency.

## M4 — Creating and managing an agent

- `bzz agent new` and `:agent new` ask the same things: name, community,
  harness, model, instructions, who may wake it, folders, picture.
- All or nothing: the key and the owner's authorization (as `broker create`
  does), the agent's folder, the agent's profile marked as a bot, and the
  owner's record of the agent with a `runtime` value for bzz.
- `agent list`, `show`, `add <channel>`, `edit`, `pause`, `resume`, `delete`;
  a panel in the TUI with each agent's state and capability record.
- bzz's agent directory stops requiring the `bot` role (D13).

**Exit:** an agent made by bzz is listed, mentioned and answered from Buzz 1.0
in a disposable sandbox, and from bzz.

## M5 — Move

- `agent move <name>`: stop, checkpoint, and pack key, memory, disk and
  settings into one file sealed with a passphrase. The agent is marked *moved
  away* here and bzz refuses to run it.
- `agent receive <file>` in another bzz.
- `agent launch-kit <name>`: for a machine without bzz, the two files and
  what `buzz-acp` needs to start our host there.
- Stopping a remote agent is Buzz's `!shutdown`; its presence is its status.
- A test at the Buzz pin that our host still reads `buzz-acp`'s prompt (D9).

**Exit:** S11 as a test with bzz on one side; a second bzz receives an agent
and continues its conversation; the moved-away copy refuses to run.

## M6 — The other harnesses

- Grok, Codex and Claude Code as P1 and M0's fourth experiment decide.
- Each gets a workspace folder bzz makes, the folders the owner grants, its
  own sandbox switched on, its own sign-in, and a tested version range.
- What they do not get: the SQLite disk, git with no real process, a move
  with memory. The capability record says so.

**Exit:** each harness answers a mention once on the pinned relay, survives a
restart with its own saved session, and refuses versions outside its range.

## M7 — Hands on this machine

- A Pi Durable agent may run real commands in a granted folder when the owner
  allows it for that agent. Each command waits for the owner's approval in
  the TUI unless he has allowed the folder without asking.
- Files go between the agent's disk and the folder by copy or by git.

**Exit:** an approved command runs in a granted folder and its result is on
the agent's disk; a refused one does not run.

## Explicit non-goals

v0.15.0 does not:

- run an agent on Cloudflare, or sync an agent between places while it runs;
- borrow other machines over SSH, or use Modal;
- give Grok, Codex or Claude Code the SQLite disk or a move with memory;
- embed a JavaScript engine in bzz, or port Pi Durable to Rust;
- add Python to the default sandbox;
- prevent two copies of one key from running in two places: Buzz does not
  either. bzz refuses to run an agent it has moved away;
- change `bzz broker` for people who bring their own agent process.

## Definition of done

1. Every milestone's exit gate passes on the fixed baselines.
2. An owner creates an agent in bzz with one command, and Buzz users see it as
   an agent.
3. A mention is answered once, whatever is killed and whenever.
4. A Pi Durable agent has its own disk with git, and reaches real folders only
   by the owner's grant.
5. An agent moves to another bzz, and to a machine with `buzz-acp`, with its
   memory and disk.
6. Each harness's capability record matches what its tests show.
7. Every row of "Testing v0.15.0" is proven in `docs/validation-v0.15.0.md`,
   or marked pending with the reason.
