# bzz v0.7.0 — Remote profile avatars

**Status:** In implementation

## Decision and goal

bzz will render profile photographs carried in the Nostr kind-0 `picture`
field, matching the useful identity cue in Buzz Desktop. This supersedes the
v0.6 local-only avatar policy. It does **not** copy Buzz Desktop source,
components, assets, configuration grammar, or tests; the comparison is solely
behavior-level research.

The default is `ui.profile_avatars = "trusted"`: valid HTTPS image URLs are
fetched as ordinary unauthenticated public resources. `"off"` retains the
current deterministic textual marker. No avatar fetch sends NIP-98,
community-membership, signing, keychain, relay-auth, cookie, or identifying
request header.

## Evidence from Buzz Desktop

At inspected upstream revision `c6e3fe7df`, Buzz Desktop maps kind-0
`picture` to `avatarUrl`, feeds it to a lazy/async `<img>` with
`referrerPolicy="no-referrer"`, and provides initials when it fails. Relay
hash-addressed `/media/<sha>` URLs use a localhost proxy; external avatar URLs
remain direct. Its timeline also proactively creates browser image requests
for unique avatar URLs. This describes product behavior only, not code to
reuse.

## Scope

### 1. Policy and configuration

- Add strict `ui.profile_avatars = "trusted" | "off"`; migrate empty config to
  `"trusted"` and fail closed on other values.
- State the exact behavior in configuration, security, release, and manual-E2E
  documentation. `off` neither queues nor fetches avatar data.
- Preserve the textual marker as the immediate fallback for disabled mode,
  invalid URL, unsupported graphics terminal, pending/failed load, or a
  missing picture.

### 2. Safe unauthenticated fetch/cache boundary

Implement a dedicated avatar client rather than reusing authenticated media:

- accept only canonical `https` URLs; reject user-info, fragments, IP literals,
  localhost, private/link-local/multicast/reserved destinations, and malformed
  hostnames;
- disable automatic redirects; optionally follow at most three redirects only
  after validating every new location with the same policy;
- use a credential-free client with no cookies, authorization, NIP-98,
  community headers, or ambient proxy settings;
- cap response bytes, image dimensions, decode work, concurrent transfers,
  distinct in-flight URLs, and in-memory/disk cache entries; accept only
  image MIME/magic supported by the existing decoder;
- key private cache paths by a SHA-256 URL digest under a dedicated profile
  avatar cache root. Never use a URL as a filename, log it in normal status, or
  cross community/identity cache boundaries.

### 3. Stable terminal presentation

- Reuse the existing serialized terminal image runtime only after an avatar
  has completed validation and local caching.
- Render an avatar as an allocated timeline image row, never an unmeasured
  overlay over a text row. Its geometry participates in scroll/viewport
  calculation and remains separate from text author labels.
- Restrict photo rendering to Kitty, Sixel, and iTerm2. Half-block and disabled
  terminals keep the textual marker; no capability probe sends a network
  request.
- Ensure stale avatar cells are cleared when scrolling, reloading graphics, or
  switching communities. A visual acceptance gate on both graphics and plain
  terminals is mandatory before release.

### 4. Ownership and lifecycle

- Avatar state/cache keys include community ID and profile pubkey plus the URL
  digest. A changed `picture` URL creates a new entry; old entries become
  prunable.
- Community/identity switch, locked mode, and `:media reload` cancel/ignore
  old generations. Avatar rendering never changes profile storage, Inbox/read
  state, subscriptions, signing, publishing, or Codex boundaries.

## Milestones

1. Typed config, URL policy, bounded client/cache model, pure tests.
2. Background credential-free fetch/decode/cache runtime with cancellation and
   pruning, plus invalid/redirect/limits tests.
3. Allocated timeline avatar rows and textual fallback across terminal
   protocols, with geometry and no-stale-cell tests.
4. Documentation, benchmarks, pinned relay journey, release-binary runner, and
   owner visual review using disposable content only.

## Acceptance criteria

1. A normal valid HTTPS `picture` renders locally in a graphics terminal after
   bounded background work; no direct text-row overlay is used.
2. `ui.profile_avatars = "off"`, locked mode, unsupported terminals, and an
   invalid URL emit no avatar network request; failed requests retain the
   marker without exposing a URL or changing any conversation state.
3. Avatar requests contain no credentials or Buzz authorization, and every URL
   plus redirect target passes the policy before connection.
4. Caches, work, and terminal geometry are bounded; switching community or
   identity cannot show an old avatar or leave terminal artefacts.
5. Existing pins, identity isolation, locked mode, Inbox semantics, and
   explicit human publication boundaries are unchanged.
