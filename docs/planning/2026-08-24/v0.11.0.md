# bzz v0.11.0 — Verified managed-agent interoperability

**Status:** Approved 2026-08-24

**Research baseline:** `block/buzz` commit
`9f55bf67456be10ff7c8238bf0d9e12e582848f6`, reviewed 2026-08-24

**Primary input:** [`docs/how-agents-works-in-buzz.md`](../../how-agents-works-in-buzz.md)

## Release thesis

v0.11.0 will let a human using bzz safely discover, inspect, mention, and
converse with an existing Buzz managed agent through the relay. bzz will verify
that the remote identity is an actual agent, distinguish its owner and public
inbound policy, and emit the exact `p` tag required to invoke it.

This release implements the first of the three independent capabilities
identified by the source review:

1. **Interact with existing agents through relay messages and exact mentions.**

It deliberately does not implement either of the other capabilities:

2. observing or controlling an existing runtime; or
3. hosting a managed local agent.

That boundary is the central product decision for v0.11.0. It provides a useful
end-to-end feature without giving bzz authority over an agent private key,
child process, ACP adapter, local tools, autonomous publisher, memory, or
observer archive.

## Why this is the next safe increment

Buzz managed agents are autonomous Nostr identities, not reply-drafting UI.
Local hosting would simultaneously introduce:

- a second key class and ownership attestation;
- executable discovery and process-tree supervision;
- ACP capability and permission negotiation;
- untrusted prompt input reaching local tools;
- per-channel queues, sessions, retries, and cancellation;
- autonomous publication under the agent key;
- encrypted memory and observer data; and
- recovery across relay, worker, and application failures.

Shipping those responsibilities as the first reintroduced `agent` surface would
make it difficult to verify the trust boundary. Remote interoperability instead
uses bzz's existing strengths: authenticated relay sessions, strict event
verification, channel membership, profiles, exact mentions, acknowledged
human sends, threads, Inbox, and offline SQLite projections.

## User-visible outcome

A user can:

1. open an Agents directory for the active community;
2. see only cryptographically verified managed agents in the primary list;
3. inspect an agent's public identity, verified owner, channel membership,
   declaration, capabilities, and effective public inbound policy;
4. understand whether the active human identity appears eligible to invoke it;
5. insert the agent into a composer through completion or the directory;
6. review the ordinary human-authored message before sending;
7. publish a kind `9` message carrying the exact agent public-key `p` tag; and
8. receive and render agent-authored reactions and threaded replies through the
   existing timeline and Inbox paths.

The UI must never imply that bzz owns, runs, can stop, or can recover the remote
agent process.

## Terminology

The implementation and UI will use these terms consistently:

- **Managed agent:** a distinct Nostr identity linked to a human owner through a
  valid NIP-OA attestation.
- **Remote agent:** a managed agent whose process and private key are controlled
  outside this bzz installation.
- **Agent owner:** the human pubkey proven by the NIP-OA relationship.
- **Verified agent:** a community bot member whose required signed public
  records and ownership relationship validate.
- **Invocation eligibility:** a local evaluation of the agent's public
  `respond_to` policy. It is advisory until send-time revalidation and does not
  guarantee that a remote runtime is online or will answer.
- **Presence:** an ephemeral relay signal, never proof that a model or tool
  runtime is ready.

The old v0.3–v0.9 one-shot Codex drafter remains retired. No migration or code
path may reinterpret its discarded `[[local_agents]]` values as remote agents.

## Product invariants

### Identity and authorship

1. Human and agent identities remain distinct.
2. bzz signs v0.11 messages only with the active human identity.
3. An agent reply is accepted only as an independently signed remote event.
4. bzz never requests, imports, stores, exports, or logs an agent private key.
5. NIP-OA proves ownership; a display name, bot role, `p` tag, profile claim, or
   public projection alone does not.

### Publication boundary

1. Choosing an agent only inserts a structured mention into the current draft.
2. The user must still perform the ordinary explicit send action.
3. Existing acknowledged-send and exact-draft recovery semantics remain
   authoritative.
4. Discovery, policy refresh, presence, reactions, and directory actions never
   auto-send a message.
5. A failed or uncertain send preserves the exact matching draft and structured
   mention metadata.

### Community isolation

1. Every agent projection is scoped by bzz community ID and normalized relay
   URL.
2. The same agent pubkey discovered on two relays produces two independently
   validated community projections.
3. Membership, policy, declaration, presence, and freshness from one community
   cannot authorize an invocation in another.
4. Switching communities invalidates open agent-directory actions before they
   can mutate a composer.
5. Locked mode exposes no new relay or signing authority.

### Privacy

1. Diagnostics may record only typed outcomes, reason enums, counts, durations,
   and queue/drop metrics.
2. Diagnostics and OTel must not contain message content, prompts, profile text,
   names, pubkeys, owner pubkeys, channel IDs, event IDs, relay URLs, or raw
   tags.
3. bzz stores only public relay records needed for the directory; it does not
   fetch or persist agent memory, observer frames, tool transcripts, private
   state, or provider configuration.
4. Public profile/declaration text follows the same rendering sanitization and
   size bounds as other remote text.
5. No remote event can introduce a local executable, command argument,
   environment variable, path, or URL that bzz executes.

## Protocol baseline and compatibility gate

The current bzz protocol baseline predates the reviewed managed-agent source.
Before implementation, v0.11.0 must deliberately update the revision-pinned
`buzz-core` and `buzz-sdk` dependencies from
`ede26863345a518ec46edd6d7692e0281883491b` to the exact reviewed revision
`9f55bf67456be10ff7c8238bf0d9e12e582848f6`, or to a newer explicitly reviewed
commit if upstream fixes are required.

The chosen commit must be recorded in:

- `Cargo.toml` and `Cargo.lock`;
- `docs/protocol-compatibility.md`;
- v0.11.0 release and validation records; and
- deterministic protocol fixtures.

The dependency update is a gate, not an incidental upgrade. Existing messages,
DMs, read state, media, profiles, search, membership, and pinned-relay journeys
must remain green before agent UI work proceeds.

No Tauri command, `managed-agents.json` field, keyring entry name, process
receipt, log format, or local Buzz Desktop database is a supported integration
boundary. v0.11.0 uses only signed relay records and authenticated relay APIs.

## Required public records

The directory projection begins with relay-authored kind `39002` membership for
the active community and a bot role. For each candidate, bzz obtains and
validates the applicable public records from the pinned protocol baseline:

- kind `0`: agent profile and NIP-OA ownership material;
- kind `10100`: agent declaration/discovery metadata;
- kind `30177`: owner-authored public managed-agent projection and inbound
  policy, when present;
- kind `20001`: optional ephemeral presence, treated only as freshness-bounded
  presentation state; and
- kind `9`: ordinary mentions, replies, and owner commands shown as messages.

NIP-AP kind `30175` definitions are not required to invoke an already-created
agent and are outside the primary v0.11 directory. Definition catalogs,
instantiation, editing, sharing, and provenance UI remain future work.

NIP-AE `30174`, NIP-AO `24200`, NIP-PMA `30179`, and usage `44200` must not be
subscribed to, decrypted, indexed, archived, or displayed by v0.11.

## Verification state machine

Candidate state is explicit and fail-closed:

```text
membership candidate
    ↓ required records fetched
records present
    ↓ signatures and coordinates valid
signed records valid
    ↓ NIP-OA links agent pubkey to owner pubkey
ownership verified
    ↓ profile/declaration and any present projection agree
verified agent
    ↓ active identity evaluated against policy
eligible | ineligible | policy-unknown
```

A candidate can instead become:

- `incomplete`: required public records are absent;
- `invalid-signature`: a signed record fails Nostr verification;
- `invalid-ownership`: NIP-OA is malformed or does not bind the candidate and
  claimed owner;
- `conflicting-owner`: public records disagree about ownership;
- `not-a-bot-member`: membership does not carry the required role;
- `removed`: current relay membership no longer includes the candidate; or
- `stale`: the freshness window expired while online refresh failed.

Only `verified agent` entries appear in the normal Agents directory and receive
an agent badge. Invalid and incomplete counts may be exposed in a neutral
troubleshooting summary, but unverified candidates must never be promoted by a
name match or cached previous state.

A previously verified record becomes non-invocable immediately after a valid
membership removal, ownership conflict, or newer invalidating replaceable
record. Historical messages remain attributed to their signing pubkeys but lose
no content and are not rewritten.

## Invocation-policy evaluation

v0.11 evaluates public policy for the active human identity:

| Public mode | Local eligibility result |
|---|---|
| `owner-only` | eligible only when the active identity is the verified owner |
| `allowlist` | eligible when the active human identity is the owner or an exact allowlisted pubkey |
| `anyone` | eligible for non-DM channel traffic |
| absent/invalid | policy unknown; no claim that invocation will run |

DM hardening follows the reviewed behavior: because v0.11 publishes only with
the active human identity, only the verified owner is shown as eligible in a DM,
even if public policy says `anyone` or includes that human as an external
allowlist member. An unknown channel type is evaluated with DM restrictions.

Policy evaluation is not authorization to use local resources: the remote
operator remains responsible for its runtime. The UI text must say “eligible to
invoke” rather than “has access,” “online,” or “will respond.”

## Send-time preparation

Agent insertion creates or updates the existing `DraftMention` using the exact
lowercase 64-character agent pubkey. Before signing the final event, bzz must:

1. confirm that the structured mention still maps to the exact visible token;
2. confirm the active composer target and community have not changed;
3. reject stale directory handles from another community;
4. while online, refresh or validate a bounded-fresh agent projection;
5. confirm current bot membership and NIP-OA ownership;
6. recompute policy eligibility for the active identity and channel type;
7. explain policy-unknown or ineligible state without destroying the draft;
8. build the normal kind `9` event with one deduplicated exact `p` tag; and
9. enter the existing acknowledged outbox path only after preparation passes.

Normal manual entry of an `@name` without a structured mention does not invoke
an agent. bzz must never infer a `p` tag from display text during final send.

If a user explicitly chooses to send an ordinary mention to a verified agent
whose policy is unknown, the UI may offer a second confirmation explaining that
the message can be published but invocation is not assured. Ineligible policy
must fail closed in the dedicated agent action. A later product decision may
permit an explicitly confirmed ordinary mention, but v0.11 must not silently
bypass the directory policy result.

## Local persistence

Add one SQLite migration, expected to be `0007_agent_directory.sql`. Exact table
names can change during implementation, but the schema must preserve these
logical records:

### Community agent projection

- community ID;
- agent pubkey;
- verified owner pubkey;
- latest profile/declaration/projection event IDs and timestamps;
- normalized public policy and allowlist;
- capabilities represented as bounded public strings;
- verification state and typed failure reason;
- membership role/current membership marker;
- last successful verification time; and
- last refresh attempt time.

### Optional bounded presence projection

- community ID and agent pubkey;
- normalized presence enum;
- source event timestamp; and
- local expiry time.

The schema must enforce community-scoped uniqueness and foreign-key cleanup.
Public records may be reconstructed from relay data; they are not an authority
for runtime ownership or process control. Cache purge follows existing
community/all behavior and deletes these projections without affecting messages,
drafts, identities, or communities.

No JSON managed-agent control store is introduced. Strict TOML configuration
gains no agent key, executable, prompt, provider credential, environment map,
or start-on-launch field.

## Synchronization and bounds

Agent directory work must not reintroduce the CPU, SQLite, or network hot loops
fixed in v0.8.0.

Required bounds:

- one coalesced directory refresh per active community;
- bounded candidate and record counts;
- bounded concurrent profile/declaration/projection fetches;
- replaceable-event selection by verified signature, coordinate, and timestamp;
- idempotent SQLite upserts that report whether state actually changed;
- no projection rebuild or redraw for duplicate relay echoes;
- quarantine of terminal subscription/query rejections until reconnect or an
  explicit refresh;
- expiring presence with no per-frame database writes;
- local input and acknowledged sends retain priority over directory traffic;
- refresh backoff with jitter and no polling while offline or locked; and
- no redraw solely because an unchanged freshness timer was checked.

All incoming strings and tag vectors receive explicit size/count limits before
allocation or persistence. A malicious community cannot grow the agent cache,
allowlist, capability list, or diagnostic cardinality without bound.

## CLI surface

The truthful managed-agent namespace returns as plural `agents`:

```text
bzz agents list [--community <uuid>] [--json]
bzz agents show <agent-pubkey> [--community <uuid>] [--json]
bzz agents refresh [--community <uuid>]
```

Properties:

- commands display public, verified relay metadata only;
- secrets and raw event bodies are never printed;
- `--json` uses a versioned schema and normalized enums;
- `show` refuses ambiguous cross-community lookup unless a community is given;
- `refresh` uses the configured authenticated community session and cannot run
  in locked mode;
- there are no `create`, `start`, `stop`, `restart`, `delete`, `logs`, `exec`,
  `prompt`, `memory`, `observe`, or `configure-runtime` commands; and
- CLI wording explicitly says remote and not controlled by this bzz process.

This namespace cannot be confused with the retired v0.3 drafter: it neither
runs a model nor produces a draft.

## TUI design

### Agents directory

Add `:agents` and a discoverable contextual action that opens a community-scoped
directory. It shows:

- profile label and deterministic fallback marker;
- verified-agent symbol;
- owner label or abbreviated owner pubkey;
- invocation eligibility (`eligible`, `owner only`, `not allowlisted`, or
  `policy unknown`);
- freshness-bounded presence when available; and
- channels shared with the active identity.

The detail pane explains:

- that the process is remotely controlled;
- which public records were verified;
- the effective public policy;
- declaration capabilities as untrusted descriptive strings;
- freshness timestamps; and
- why invocation is unavailable, without exposing raw signed records.

The directory supports narrow and wide layouts, keyboard-only operation, mouse
hit testing, focus restoration, resize, lock, community switch, and safe
terminal cleanup.

### Composer integration

Verified eligible agents appear in `@` completion with a distinct symbol and
owner/policy context. Selecting one uses the existing structured mention model.
Human members remain available and are visually distinct.

An “Mention in composer” action is enabled only when there is an exact active
composer target in the same community. It inserts text but never sends. Duplicate
selection must not produce duplicate `p` tags.

### Timeline and Inbox

Messages continue to render from their signed author profile. A verified-agent
badge may be added using the community-scoped projection. The badge is
presentation only and must disappear when verification is revoked without
altering historical authorship.

Agent replies, reactions, and thread activity use existing unread, thread, and
Inbox semantics. v0.11 introduces no separate AI transcript, hidden reply,
auto-read behavior, or special content retention.

## Architecture modules

Expected independently testable modules:

```text
src/agents/
  mod.rs          public types and service boundary
  protocol.rs     record parsing and coordinates
  ownership.rs    NIP-OA verification
  policy.rs       normalized inbound-policy evaluation
  directory.rs    community-scoped projection/reconciliation
  service.rs      read models and explicit refresh

src/store/
  agents.rs       idempotent SQLite projection operations

src/ui/
  agents.rs       directory and detail presentation
```

The exact layout may evolve, but protocol verification, policy decisions,
persistence, and rendering must not collapse into `app.rs`. No module may import
process-spawning APIs.

## Deterministic test matrix

### Protocol and ownership

- valid bot membership + profile + declaration + NIP-OA + projection;
- valid owner-only, allowlist, and anyone policy;
- profile signed by the wrong key;
- malformed auth tag;
- auth tag binding another agent;
- projection signed by a non-owner;
- conflicting owner claims;
- declaration pubkey/coordinate mismatch;
- duplicate and reordered replaceable records;
- far-future timestamps rejected by existing clock policy;
- oversized tags, capabilities, names, allowlists, and content;
- bot role absent or membership removed; and
- same pubkey on two communities with different owners/policies.

### Policy

- active identity is owner;
- active identity is explicitly allowlisted;
- active identity is neither;
- anyone in a normal channel;
- anyone/allowlist in a DM still fails closed;
- unknown channel type uses DM restrictions;
- absent policy remains unknown rather than becoming anyone;
- stale policy cannot override a newer valid replacement; and
- community switch recomputes against the new active identity.

### Draft and send

- selection inserts exact mention metadata;
- edited mention invalidates structured metadata safely;
- repeated selection deduplicates `p` tags;
- same display name cannot retarget another pubkey;
- stale completion result cannot cross community/composer targets;
- membership removal before send preserves the draft;
- online refresh failure preserves the draft;
- rejection and ambiguous ACK preserve the exact draft;
- accepted ACK removes only the acknowledged revision; and
- no selection, refresh, presence, or reply auto-sends.

### Projection and runtime behavior

- cold online discovery;
- offline startup from a previously verified bounded cache marked stale as
  applicable;
- reconnect refresh;
- duplicate WebSocket/HTTP delivery is a no-op;
- closed subscription/query is not retried in a hot loop;
- presence expires without SQLite or redraw churn;
- membership removal revokes the badge/action;
- cache purge leaves messages and identities intact;
- diagnostic queue saturation remains bounded; and
- sustained directory traffic does not starve input, attachments, sends, or
  channel switching.

### UI

- wide list/detail and narrow drill-down snapshots;
- keyboard and mouse selection;
- composer insertion and focus restoration;
- policy warning/unknown states;
- lock and community-switch dismissal;
- terminal resize and cleanup;
- sanitized hostile profile/capability text; and
- agent/human distinction without relying only on color.

## Security review checklist

- [ ] No agent secret exists in config, SQLite, keychain, environment, process,
      command arguments, logs, reports, tests, or release fixtures.
- [ ] No remote field reaches process spawning, shell evaluation, filesystem
      paths, environment construction, or automatic URL opening.
- [ ] NIP-OA and every source event are verified before an agent badge appears.
- [ ] Owner-authored and agent-authored records cannot substitute for one
      another.
- [ ] Community and active-identity isolation hold in storage and UI handles.
- [ ] Policy absence and ambiguity fail closed.
- [ ] DM policy is stricter than normal-channel policy.
- [ ] Agent content follows existing Markdown, media, profile, and cache safety.
- [ ] Diagnostics/OTel retain the v0.9 content-free allowlist boundary.
- [ ] Human acknowledgement-aware send remains the only local publication path.
- [ ] Removal or invalidation cannot silently retain invocation authority.
- [ ] Bounded caches, queries, lists, strings, and retries are demonstrated by
      tests.

## Release gates

### Local deterministic gates

- `cargo fmt --all -- --check`;
- strict locked all-target/all-feature Clippy;
- locked tests for all targets;
- protocol/property tests for all verification and spoofing cases;
- store migration and downgrade-safe backup coverage;
- `cargo deny check` and `cargo audit` against the accepted baseline;
- release build and isolated `bzz check`;
- CLI JSON schema snapshots and shell completions; and
- zero unbounded growth in directory stress tests.

### Cross-platform gates

- Linux, Windows, Intel macOS, and Apple Silicon macOS release builds;
- target-OS identity/keychain regression suites remain green;
- TUI directory and composer behavior is platform-independent; and
- no process-management or ACP code is conditionally hidden on one target,
  because none belongs in this release.

### Relay integration gates

- pinned Buzz relay starts from the documented exact source revision;
- deterministic owner/agent fixture establishes membership and valid public
  records;
- bzz discovers only the valid agent;
- exact human-authored `p`-tag mention is accepted;
- deterministic agent-signed reaction/reply returns and projects correctly;
- spoofed/incomplete candidates never receive a verified badge;
- membership removal revokes invocation eligibility; and
- reconnect/duplicate delivery remains idempotent.

The integration proves protocol interoperability, not that a model, ACP adapter,
or autonomous local tool ran.

### Manual Herdr acceptance

Unlike v0.10.0, v0.11.0 introduces visible interaction and requires a controlled
Herdr acceptance run with disposable protocol-free fixtures. Capture:

- wide and narrow Agents directory;
- details and policy explanations;
- keyboard and mouse selection;
- exact composer insertion;
- community switch and lock dismissal;
- resize/focus restoration; and
- no terminal corruption after exit.

No real agent key, model credential, message content, or production community is
used in the visual run.

### Publication gates

- tag resolves to the fully validated commit;
- expected archives/installers, checksums, SBOM, and attestations publish;
- every checksum and provenance subject verifies;
- downloaded Linux binary reports v0.11.0 and passes isolated `bzz check`;
- downloaded `bzz agents` output proves remote-only wording and versioned JSON;
- native-keychain and encrypted-file identity smoke remain green; and
- published verification evidence records exact workflow and artifact results.

## Explicit non-goals

v0.11.0 does not:

- create, import, back up, or own an agent Nostr key;
- mint NIP-OA attestations;
- create or publish managed-agent projections or definitions;
- add an agent to a channel or assign a bot role;
- spawn `buzz-acp`, Codex, Claude, Goose, Buzz Agent, or a custom executable;
- install, authenticate, probe, or select a model/provider;
- pass credentials or environment variables to a child;
- maintain ACP workers, per-channel ACP sessions, steering, queues, retries, or
  dead letters;
- provide tool permission approvals;
- publish autonomously as an agent;
- subscribe to or archive observer telemetry;
- issue observer controls, `!cancel`, `!rotate`, or `!shutdown`;
- read or write NIP-AE memory or usage metrics;
- support provider-backed deployment;
- claim control of remote presence or readiness; or
- claim Buzz Desktop managed-agent feature parity.

## Follow-up architecture gates

A future local-hosting release requires a new plan and ADR that resolve, before
implementation:

1. whether bzz ships a revision-pinned `buzz-acp` sidecar or independently
   implements the relay/ACP harness;
2. how agent keys are isolated from human identities and transferred without
   command-line or persistent plaintext exposure;
3. whether agent-configured credentials use dedicated keychain entries rather
   than restricted JSON;
4. how child environments are allowlisted instead of inheriting ambient bzz
   secrets;
5. whether ACP permissions default to deny, interactive approval, or an
   explicitly acknowledged bypass mode;
6. how autonomous agent publication is separated from the human outbox and
   diagnostics;
7. how process trees, receipts, nonces, crash circuits, updates, and orphan
   cleanup work on all four release targets;
8. which queue, retry, steering, timeout, and dead-letter semantics are durable;
9. whether observer archives are default-off and how their content retention is
   disclosed; and
10. what compatibility commitment bzz makes to provisional ACP v2 and
    Buzz-specific `_meta` fields.

Passing v0.11.0 does not pre-approve any answer to those questions.

## Definition of done

v0.11.0 is complete only when:

1. the exact Buzz protocol baseline is pinned and documented;
2. verified remote agents are community-isolated and spoof-resistant;
3. owner and public policy are understandable in CLI and TUI;
4. exact agent mentions survive the full acknowledgement-aware draft lifecycle;
5. a deterministic relay fixture completes mention → reaction/reply without any
   LLM or local agent process;
6. invalid, incomplete, stale, removed, and cross-community candidates fail
   closed;
7. diagnostics remain content-free and runtime resource usage remains bounded;
8. all deterministic, cross-platform, pinned-relay, Herdr, security, and release
   gates pass; and
9. release language says **remote managed-agent interoperability**, never local
   hosting, runtime control, or feature parity.
