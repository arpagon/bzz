## Release thesis

Since v0.15 bzz runs agents. They can only talk. v0.16.0 lets **an agent
write a small app for a channel, which bzz draws beside the conversation,
and whose state the people and agents of the channel share**.

An app is four things, placed separately:

| Piece | Where it lives | Rule |
|---|---|---|
| Its **script** | one Lua file in bzz's data directory, on the machine of whoever installed it; it can be offered to the channel | it runs inside bzz with only what bzz lends it; a version the owner did not write himself runs only after he approves it |
| Its **brief** | a short text kept with the script | it says what the app does and what its records hold, so that a person can judge it and another agent can write the same app for another client |
| Its **records** | NIP-AR artifacts in the channel | bzz signs them; the script never sees a key, and reaches only the record types it declared |
| Its **pane** | a region of the TUI | bzz draws it; the app has no terminal of its own |

The owner's guiding example: someone asks an agent to add a priority and a
filter to the channel's task board. The agent changes the script, the owner
approves the change, and the board updates in place, without a restart and
with the selection and the search still there.

## What was tried first

Three rounds of experiments, 51 subagents, one bench that drives any terminal
program and reads its screen.

| Question | Result |
|---|---|
| Does the relay carry a shared app? | Yes, at the pin. A custom artifact type is accepted. Another participant's change arrives in milliseconds. In 100 simultaneous edits of one record, none was lost. |
| What limits does it set? | 60 writes a minute and 50 in five seconds per identity, shared with chat. 4096 live artifacts in one sync, counted over what its filter matches. A conflict does not carry the current head. |
| Can a mini-app use the data without the key? | Yes. A bridge that holds the key served four different hosts unchanged. |
| React, as Buzz desktop plugins use? | It works in a terminal two ways. Dropped: Buzz plugins do not travel between clients, and agents wrote every option correctly on the first try. |
| A WebAssembly widget? | The only strict sandbox, but written in Rust: a compile step and 11.2 MB. Dropped. |
| A declarative file, no code? | It carried none of four new tasks completely, the owner's example included. Dropped. |
| TypeScript in Node, drawn by bzz? | It carried every task. 94 MiB per app, and its isolation is a set of blocks on what Node offers. Not chosen. |
| **A Lua script inside bzz?** | **It carried every task.** 6 MiB per app, first draw in 13 ms, reload in about 30 ms, and the script has no file, network, process or environment to reach. Chosen by the owner. |
| Can agents write these apps? | Nine fresh agents wrote four different apps for the Lua host from a 120-line guide and a contract file. Seven passed every case on the first run of the bench. The other two failed one case each on a gap in the host (no JSON `null`), since closed. |
| Does a change appear live? | Yes. 200 saves over eight agent-written apps: data, selection, filter, an open form and the connection survived every time. |

What the experiments did not cover is the work of this release: the app
inside bzz's window, on bzz's own artifact service, with the owner's approval
in between, on four platforms.

## How Buzz does it, and what bzz takes

Read in `block/buzz-app` at `949034f`; nothing was run.

| | Buzz desktop | bzz v0.16.0 |
|---|---|---|
| **What the agent is told** | A bundled plugin gives the agents of the device three tools: `plugin_authoring_guide`, which returns the guide that ships with Buzz, `plugin_status` and `plugin_reload`. Nothing is put in the agent's prompt until it asks. | The same shape: a tool returns the guide and the contract (M5). |
| **How the agent writes** | It writes files in a folder with its own access to the disk. The owner installs the folder once by hand; afterwards the agent reloads it. A change of host access goes back to the owner. | The agent has no folder to write to. It proposes a script through a tool and the owner approves the bytes, every time (M4, M5). |
| **How a plugin reaches another person** | Never through the relay. Each person installs it: from a folder, from a Git repository at a commit, or from a URL with its SHA-256. A plugin can ask its owner to install another, and an administrator can recommend pinned sources. The receiver always reviews. | Through the channel: the script travels as an artifact and waits for the receiver's approval (M6). |

bzz can send the bytes where Buzz sends a reference because the two things
differ: a Buzz plugin is up to 8 MiB of code with the reach of the app; a bzz
script is a few kilobytes with no reach beyond its records.

Code does not cross between the two clients: a Buzz plugin is React, a bzz app
is Lua. What crosses is the records and the brief.

## Design

```text
 an agent ──tools──▶ bzz ──asks──▶ the owner
                      │ approved
                      ▼
               the app's script ──▶ interpreter (its own thread, closed API)
                                      │ view            │ records
                                      ▼                 ▼
                                 the app pane      artifact service ──▶ relay
```

- **The runtime** is the prototype brought into bzz (`src/apps/`; the
  prototype's host is 2,365 lines of Rust). One interpreter per open app, on
  its own thread. The script returns a tree of widgets; bzz lays it out and
  draws it with Ratatui. A call that runs too long is stopped; memory is
  capped.
- **The contract** is one document, `docs/app-api.md`, marked `api = 1`: the
  functions a script defines, the 18 widget elements, and the record calls.
  It is the prototype's contract with the changes the relay test asked for:
  an opaque revision instead of a number; an explicit order field instead of
  sortable ids; a `rate_limited` answer that says how long to wait; the
  published limits.
- **Records.** bzz today changes only an artifact's envelope: rename, delete,
  restore, move. Apps need records created and updated with content. On a
  conflict bzz reads the head and gives the script the current record; what
  to do with it is the script's rule, because a board merges and an approval
  must not.
- **The pane** sits to the right of the conversation. It needs 40 columns
  inside its border; the conversation keeps its 30. While the pane has the
  focus, keys go to the app, except `Ctrl+C`, which bzz keeps to leave it.
- **Approval.** A script version that came from an agent is shown to the
  owner with the record types it declares and its difference from the
  running version. Approval is of exact bytes. A version that fails to load
  leaves the previous one running.
- **Agents** get tools to read an app, to try a script and see the screen it
  draws, and to propose a version. They never write the file themselves.
- **The brief** is kept with every app: what it does, its record types and
  their fields, in plain text. The agent that writes the script writes the
  brief. It is what a person reads before approving, and what an agent in
  another client, Buzz included, needs to write its own version over the same
  records.
- **Sharing.** The owner can offer an app to a channel. Script, manifest and
  brief travel as one artifact of the channel, signed by him. Another bzz in
  the channel shows the offer with its author; nothing runs until that
  person approves the exact bytes. A new version is a new offer.

## Cross-cutting rules

The thirteen rules of v0.13 to v0.15 still apply. Five are added:

14. **A script gets only what bzz lends.** No file, network, process,
    environment or native code. Everything a script can do is a function in
    `docs/app-api.md`.
15. **A script cannot stop bzz.** Each call has a time budget and the
    interpreter a memory cap. A failing or stuck app says so in its own pane;
    the conversation keeps working.
16. **Nothing runs that the owner has not approved.** Approval is of exact
    bytes and shows what the script declares, and who it comes from: an
    agent, or a person of the channel. A change of declared record types is
    always shown as such.
17. **Records are fenced.** An app reads and writes only the record types it
    declared, in the channel it is open in. bzz checks it where it serves the
    call.
18. **The contract has a number.** A script says `api = 1`. bzz refuses a
    number it does not know and says which it knows.

## What M0 changed

M0's answers are in `docs/adr-v0.16-apps.md` and
`docs/validation-v0.16.0.md`. None changed a decision or the order of the
milestones. They changed this:

- **Stopping a script (M1).** The prototype's way fails 32 of 80 hostile
  scripts. Lua 5.4 stays (D1), with three changes: the hook makes the script
  yield and bzz never resumes it; a bounded library replaces 16 of Lua's
  functions; every call goes through one entry function and bzz reads a
  script's tables raw. An author loses `__gc`, an `xpcall` handler at the
  point of the error, and a stable sort. A script has a size cap.
- **The interpreter costs 0.40 MiB,** and the bounded library about 0.13
  (D12 said 0.6). With the runtime, the store, the pane and
  the tools, apps add about 3 MiB to the release binary.
- **Limits (M2).** 4096 is per sync filter, so an app is limited by its own
  records: bzz sets 1000 live records for an app. A refused write costs
  quota, so bzz checks before it sends. Type names are
  `bzz.app.<app>.<record>`.
- **M2 is larger.** Besides the artifact service and store it changes the
  connection supervisor, which must say why a sync was closed, and the
  store, which must replace records by type. Ordinary chat events close a
  sync; the pane stays drawn across a resync. An archived channel refuses
  writes and the pane says so.
- **Who wrote a record** is whoever signed its last revision; any member may
  revise any record. The contract says which identity a script is given,
  and that a rule such as "you cannot decide your own request" rests on a
  field any member can set.
- **The pane (M3)** is 42 columns with its border, docked from a window of
  72 columns and 22 rows; thread and app together from 144. `Ctrl+C` leaves
  the app. bzz enables bracketed paste, which it never did; that also fixes
  pasting several lines into the composer. The Board template is brought
  down from 60 columns to 40.
- **Sharing (M6).** An offer is one revision and its signer: any member can
  publish a new revision of someone's offer, and that is a new offer from
  that member. A script is at most 128 KiB and a brief 16 KiB. Sharing an
  app also posts its brief as a message, because Buzz desktop shows nothing
  else.
- **Buzz desktop (D11)** 1.0.1 shows nothing of an app's records and is not
  harmed by them.
- **M7.** On a relay that requires membership the agent's key must be
  admitted; the gate says which mode it ran in.

## M0 — Baseline and the unknowns that can change the plan

- Fix the baselines. Add `mlua` behind the `apps` feature; record the size of
  the binary with and without it, `cargo deny check` and `cargo audit`.
- ADR "apps": bzz runs code it did not ship. The v0.15 plan listed "embed a
  JavaScript engine in bzz" as a non-goal; this embeds a Lua interpreter with
  a closed API, and says why that is a different thing.
- Six questions, each with a recorded answer, before M1 is designed in detail:
  1. `mlua` with vendored Lua builds and passes its tests inside bzz on the
     four CI platforms and the five release targets. bzz already compiles C
     there (bundled SQLite, `aws-lc-sys`).
  2. **The call that cannot be stopped.** In the prototype a pathological
     `string.find` runs on until bzz exits. Choose between bounded string
     functions in Lua 5.4 and Luau, by whether every call can be stopped.
  3. **Records on the pinned relay:** the rule for type names (one attempt
     was refused as "invalid namespaced artifact type"), how to sync only
     one app's types, what bzz does near 4096 live records, and whether a
     script with its manifest and brief fits one artifact.
  4. **What Buzz desktop does with these artifacts** in a channel it shares
     with bzz, in a disposable sandbox as in v0.15: whether they show, clutter
     or break anything.
  5. **The pane and the keys:** at which window widths conversation, thread
     and app fit, and which key leaves the app. A throwaway layout, tried in
     Herdr.
  6. The Ratatui widgets the contract uses are available under bzz's own
     feature set.

**Exit:** the baselines build on four platforms; the six answers are recorded.

## M2 — Records

- Content-level create, update and delete of artifacts for app types, on the
  existing artifact service and store. Sync of one channel's records for the
  declared types.
- Conflict: bzz reads the head and hands the script the current record.
- Order: a field in the record, not the identifier.
- Quota: app writes take a class below a person's messages in the admission
  scheduler. Past the relay's quota the script gets `rate_limited` and the
  wait, and the pane can say it.
- The fence of rule 17, and the published limits.

**Exit:** two bzz profiles on the pinned relay share a board: a change
arrives live, a simultaneous change loses nothing, a restart shows the same
records. A script that asks for an undeclared type is refused. At the quota
the pane shows the wait.

## M3 — The app pane

- The pane in the layout, with the thread pane and at narrow widths, as M0
  decided. Zoom.
- Focus and keys: a new pane in the focus order; keys to the app while it has
  the focus; paste as one piece of text; the key that leaves.
- `:apps` lists them; `:app open <name>`, `:app close`. The status line shows
  an app's error.
- Colours come from bzz's theme.

**Exit:** Herdr scenarios on the release binary: open an app, type in it and

## M4 — Installing, approving and managing

- Store: `<data>/apps/<community>/<name>/` with the script, a small manifest
  (name, title, `api`, record types), the brief of D16, and the earlier
  versions. Migration 21
  records what is installed, where it is open, the approved hash and who
  proposed it.
- The approval overlay, on v0.15's: who it comes from, the brief, declared
  types, size, and the difference from the running version. Refusal with a
  reason.
- A version that fails to load is not installed; rollback to an earlier one.
- `bzz app list|show|add|remove|enable|disable|check|try|dev|new`. `check`
  loads a script and reports errors; `try` prints the screen it draws.
- The three templates of D9. `docs/apps.md`.

**Exit:** a script added from a folder runs only after approval; a failing
update keeps the old version; rollback works; `app dev` reloads on save;
uninstalling leaves the channel's records alone.

## M5 — Agents write and change apps

- Tools, served as the v0.15 tools are, to all four harnesses: list the apps
  of the conversation's channel, read one, **try** a script (bzz loads it
  apart, feeds it keys, and returns the screen as text and any error),
  **propose** a version with its brief, and fetch the author guide and the
  contract (D17). The guide is the experiment's, brought to `api = 1`.
- `:app brief` posts an app's brief to the channel as a message.
- A proposal opens the approval of M4. The agent is told the outcome: applied,
  refused with the owner's reason, or failed to load with the error.
- The capability record of each harness says whether it can author apps.

**Exit:** with the scripted harness: propose, approve, and the open app
changes in place; refuse, and nothing changes; a script with an error comes
back to the agent with file and line. With real models, by D13: on a mention,
each supported harness adds the priority and the filter to the Board, and the
result passes the bench's cases for that change, and its brief says what the
script now does.

## M6 — Sharing an app in the channel

- `:app share` publishes the open app to its channel as one artifact: script,
  manifest and brief, signed by the owner.
- Another bzz in the channel shows the offer: who shares it, the brief, the
  declared types. Approving installs and opens it. Nothing is fetched from
  anywhere else, and nothing runs before approval.
- A later version is a new revision of the same artifact and a new offer,
  with the difference from the installed one. It is never applied by itself.
- Withdrawing an offer deletes the artifact; installed copies stay.
- An agent's proposal that the owner approved is offered only if he shares it.

**Exit:** on the pinned relay, with two profiles: one shares the Board; the
other sees the offer, approves it, and both use the same records. A version
with a changed type list is shown as such. A tampered or oversized artifact
is refused. An offer from someone who cannot write to the channel never
arrives.

## M7 — Agents use an app's records

- Tools to list and write the records of an app open in the conversation's
  channel, inside rule 17, signed with the agent's key by bzz.
- The app's script is not involved: an agent takes part without a screen.

**Exit:** scripted: an agent takes a day in the Rota and another profile sees
it. On the pinned relay: the same, with the agent's `bot` role. A write
outside the declared types is refused.

## Explicit non-goals

v0.16.0 does not:

- run Buzz desktop plugins, React, TypeScript or WebAssembly;
- install a script from Git or a URL, offer a catalogue, or apply a shared
  version without the receiver's approval;
- ship a Buzz desktop plugin that draws the same records;
- offer a declarative app format;
- give an app the mouse, images, sound, the network, files, timers finer
  than a tick, or calls into another app;
- open an app in a direct message;
- merge concurrent edits by itself: what a conflict means is the script's
  rule;
- make other clients obey an app's rules: the relay checks who may write to
  the channel, not what a record says;
- show who else has the app open, or where their cursor is;
- change agents, harnesses or the broker beyond the new tools.

The follow-ups carried from v0.15.0 (the tracker `TODO-cf8fcefa`) stay where
they are; this plan neither closes nor depends on them.

## Definition of done

1. Every milestone's exit gate passes on the fixed baselines.
2. The owner opens an app beside a conversation, and two people in the
   channel see each other's changes.
3. An agent, asked in the channel, changes that app; the owner approves; the
   change appears without a restart.
4. A script reaches no file, network, process or environment, and cannot
   stop bzz.
5. No script version runs without the owner's approval of its exact bytes.
6. The contract `api = 1` is one document, and the shipped templates and
   fixtures are written against it. Every app has a brief.
7. If M6 ships: an app offered in a channel runs on another person's bzz
   after that person's approval, and not before.
8. Every row of "Testing v0.16.0" is proven in `docs/validation-v0.16.0.md`,
   or marked pending with the reason.

## How the work is done

- Experiment, then tracked plan, then branch and pull request. No push, merge,
  tag, publication or deployment without the owner's word.
- Milestones are built by subagents in worktrees and reviewed by the
  principal, who runs every gate again himself.
- `unsafe` stays forbidden in bzz's own code. Each new dependency is justified
  and passes `cargo deny check` and `cargo audit`.
- Migrations are never edited once merged.
