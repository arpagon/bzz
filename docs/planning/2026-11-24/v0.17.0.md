# bzz v0.17.0 — The first minute, and everything within reach

**Status:** Built 2026-11-25; release candidate, not released (see "How it
closed", at the end). Approved by the owner on 2026-11-24. He accepted the decisions as
proposed, widened D7 to all the visualizers, and asked whether others had
solved what D3 first proposed to solve with a helper program; a second study
replaced it. He allowed the branch and a draft pull request from the first
day (D14) and the use of his Windows and macOS virtual machines (D15). D13,
the film, is decided on Saturday.

**Written from** five research tasks in the experiment
`runs/experiments/bzz/v017-tui-2026-11-24/` (reports in Spanish, designs in
English, prototypes with images and video). "Evidence" at the end says who
measured what.

## Why now

bzz is announced on **Tuesday 2026-12-01** (Show HN, one post on X). A person
who reads the announcement runs one line and decides in a minute. On
2026-11-24 that minute failed:

- The published v0.16.0 installs in 3 to 4 seconds on a clean Debian 13 or
  Ubuntu 22.04 and then does not start: `libasound.so.2` is missing.
- There is no way to see bzz without a Buzz community and an identity.
  Another terminal client for Buzz already has a built-in demo.
- Inside bzz, 46 of 114 actions can be reached only by knowing a word typed
  after `:`. No screen lists those words. `?` shows 18 of 45 keys at 80×24.

## Release thesis

**v0.17.0 makes bzz easy in its first minute and good to look at.** A
newcomer runs `bzz demo` and is inside a living team in under a second. One
key, `Ctrl+K`, finds and runs any action. A huddle shows who is speaking and
whether your microphone works. The screen shows where the focus is, what is
new, and what to do when there is nothing.

Nothing in v0.17.0 changes the protocol, the store or the app contract.

## Two waves and a cut line

The version is built in two waves, so that an ambitious scope cannot put the
announcement at risk.

- **Wave 1, the floor** (Wednesday 25 and Thursday 26). Everything a newcomer
  meets in the first minute, in its simplest form. On Thursday night wave 1
  alone is a version that could be released.
- **Wave 2, the ambition** (Friday 27 and Saturday 28). The larger pieces:
  the registry behind the palette, joining a community inside the interface,
  the zoomed visualizer with its styles, motion, layout, the mouse. Each
  piece merges only if its gate is green by Saturday 18:00.

**The date wins over the scope.** What misses Saturday goes to v0.17.1, the
week after the announcement. Two things cannot be cut; if either is missing,
the announcement moves, not the gate:

1. bzz starts on a clean Linux machine, or says in one line what to install.
2. `bzz demo` works offline.

**What is likely.** Wave 1 holds about fifteen agent-days of work and wave 2
about twenty. The machine builds well for five or six agents at a time, so
four days give twenty to twenty-four. Wave 1 fits with room. Of wave 2 the
small and medium pieces fit; the two large ones (C8, A9) are the ones that
may slip. This is an estimate from v0.16.0's pace, not a measurement.

### Why this way (D3)

On Linux a program names, in its file, the libraries it needs. The system
loads them before the program's first instruction. If one is missing, the
program never runs: bzz cannot print a message, open the demo or even answer
`--version`. bzz names the sound library because the audio crate links to it,
though only a huddle uses it.

The first draft proposed a helper program. The owner asked whether others had
solved this; a second study read how they do it and built each way.

| Way | Result |
|---|---|
| **Speak the sound server's protocol in pure Rust** (the crate `pulseaudio`, MIT), on Linux only | **Chosen.** Built in a copy of bzz: the binary names no sound library, starts on clean Debian, Ubuntu and AlmaLinux, and bzz's own audio test passes on PipeWire and on PulseAudio. A round trip takes 37 ms against 170 ms today. +299 KB, no C compiler, no `unsafe`. |
| The audio crate's newer version, which has this built in | It still names the ALSA library. Making that optional is an open request upstream. |
| The audio library of Firefox, or SDL | Both start without the library, and both bring a C or C++ build with cmake. One linked another sound library by default; the other crashed on bare ALSA. |
| The library shipped beside bzz | Broke sound on a desktop that has the library (AlmaLinux 9). |
| A helper program | A second binary and a protocol between the two, for less: it still has no sound where there is a sound server and no ALSA library. |
| Only say what to install | The fallback. |

What it costs: a machine with ALSA and no PipeWire or PulseAudio in the
session has no huddle audio, and bzz says so. Desktops of the last years run
one of the two. Not proven yet: the macOS and Windows builds with this
change, a real call on the test relay, and WSL.

## Cross-cutting rules

The eighteen rules of v0.13 to v0.16 still apply. Five are added:

19. **Nothing that worked stops working.** Every key and every `:` command
    of v0.16.0 does what it did, except where a decision above says
    otherwise. A test pins the list.
20. **Nothing moves while nothing changes.** At rest bzz draws no frame and
    writes no byte. A waiting key is handled before a frame of an animation.
    All motion can be turned off, and the end state then shows at once.
21. **Colour is never the only signal.** Focus, unread, speaking and muted
    are readable under `NO_COLOR` and with 256 colours.
22. **The demo is closed.** It opens no connection outside the machine, reads
    and writes nothing of a real configuration, and the screen says at all
    times that the data is generated.
23. **One place says what an action is.** The palette, the help, the hints
    and the `:` line read the same table. In v0.17.0 that table is static;
    the generated key map comes after.

## Explicit non-goals

- An interface inside the conversation, a chart element in the app API, or
  any change to `api = 1` (D10).
- A change to the protocol or the store; a migration.
- Use of the palette remembered between sessions (it would need a
  migration).
- Panes that open with an animation (a risk with image protocols).
- A glibc below 2.34 and a musl build.
- Huddle audio on a Linux machine with ALSA and no sound server (D3).

## Definition of done

- The two things of the cut line hold on the published binary.
- Every item that ships has its proof recorded in
  `docs/validation-v0.17.0.md`; every item that does not is named in the
  release notes' known limits and in the plan's closing section.
- The gates are green: format, clippy, tests, no-default-features, deny,
  audit, the relay suite, the upgrade test, the scenarios.
- CI on `main` is green.
- The README and getbzz.dev say what a person needs and how to try it in a
  minute, and both are true on a clean machine.

## How the work is done

As v0.16.0: subagents in worktrees, one brief each, under the rules in
`runs/v017/`; the principal reviews each delivery, runs every gate again and
merges. No push, tag, release or deploy without the owner's word. No real
model and no paid service is needed to build this version; the demo's agent
is scripted and the screen says so.

**Where the build departed from the plan, and why.**

- **The helper was replaced before building** (D3). The owner asked
  whether others had solved what the first draft solved with a helper
  program; a second study built each way, and bzz speaks the sound server's
  protocol itself. The plan's D3 and "Why this way" were written after that
  study, before the build began. Measured in the end: a round trip of 13 to
  26 ms through PipeWire, against the study's 37.
- **`u` marks the channel unread,** not "unread from here" (D5, C7).
  Marking from a message needs read-mark work the store does not have; the
  palette's row and the key map say "Mark this channel unread".
- **Toasts, and D10.** L7 asked for "a toast instead of `Saved.` in the app
  pane". `Saved.` and `Loaded N cards.` are the app's own text (`ui.text`);
  making them toasts needs a new host call, a change to the app contract
  that D10 forbids. Toasts carry bzz's own confirmations instead
  (attachments, copies, the sidebar).
- **B8 was not built.** Task `viz2` measured the frame of each style and
  advised building B8 after the loop that sleeps (L9). L9 landed late in
  the day; B8 goes to v0.17.1. The visualizer redraws the whole screen while
  it moves.
- **B2 and B3 were proven on the engine, not on a recorded call.** The plan
  asked for a tape on the test relay where a name appears while that
  person's tone plays. Sound servers may run here only inside containers,
  and joining a huddle in the interface needs a device, so the proof is the
  real engine on the pinned relay with generated frames (a late joiner named
  and his level on the meter while his tone plays), with goldens for what
  is drawn. A call between two clients through PipeWire in containers was
  run later, for E1.
- **W2's paste.** The terminal library bzz uses gives no paste event on
  Windows. The writing dock keeps a paste's lines (a line break with more
  keys waiting is a new line); elsewhere a paste acts as keys. It is a known
  limit of v0.17.0; reading the console's input as VT sequences, which would
  give a real paste, is for after the announcement.
- **The widths moved.** L10's table keeps the conversation at 38 columns
  (v0.16: 30), so every threshold of v0.16 at which a pane shows moved
  (the release notes give each number), and a v0.16 scenario moved with
  them (`t16-app-pane`).
- **`Esc` moved** (L12): a v0.16.0 binding that changes, pinned as a
  deliberate change beside D5 and D6. Building `z` (L10) showed that a
  v0.16.0 key map could use a key v0.17.0 adds as the start of a sequence
  and make bzz refuse to start; a user's binding now wins in its scope.
- **The scenario suite.** Each task ran the suite on the pinned relay; no
  run passed whole, because scenarios of v0.16 leave state that later ones
  trip over, and some lines wrap at 80 columns. A task of its own (`suite`)
  was started at the end to make the suite pass in any order and at 80×24.
- **Two tasks not in the plan.** `tidy`, for the loose ends of the reviews
  (the Board's `q` in the demo, `:huddle devices` with no server, tests
  that failed under load, `docs/themes.md`, `bzz demo --help`), and `ci`,
  for an audio job that hung in CI.

**Decisions the principal took during the build.**

- The draft pull request was pushed from the first day (D14), and once the
  head was pushed before his own full gates, to get the three systems' CI
  early. CI keeps each system's release binary three days on a pull
  request, for hands-on checks; W2 was walked with Windows's.
- One target directory per checkout, and the gates in a checkout of their
  own, after a gate run shared a build with another checkout. The no-default-
  features clippy, which only CI ran, joined the gates.
- `scripts/tui-herdr-scenarios.toml` is merged scenario by scenario, by id,
  after a merge that interleaved two sides corrupted five scenarios.
- The version commit waits on a branch of its own and is placed last, on
  the candidate. The agent host stays 0.16.0: nothing in it changed, and a
  new version would make every `pi-durable` agent install again.
- A setting v0.17.0 adds is written to `config.toml` only when it is not
  the default, so that v0.16.0, which refuses unknown settings, can still
  open a profile v0.17.0 saved; checked at each later merge.
- The `pulseaudio` crate is built optimised in every debug build
  (`Cargo.toml`, no new dependency), after its unoptimised build starved
  playback in CI.
- The seams between tasks were joined at merge: the first screen's `j`, `p`
  and `k` and `:community add` open the join form; the join form in the
  demo says that joining needs a real community.
- W2's paste is a known limit; B8 goes to v0.17.1.
