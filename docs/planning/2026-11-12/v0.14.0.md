# bzz v0.14.0 — Buzz 1.0 era

**Status:** Proposed 2026-11-12. The owner answered D1–D5 the same day: edit
own messages, a real Buzz 1.0 pairing in a disposable sandbox, read and write
Solo chats and sections, the latest pin, and search paging.

**Prerequisite:** v0.13.0 is published (2026-11-11, `2b3429f`).

**Protocol baseline:** move from `block/buzz`
`f3b127e3af5c14d2314faa2b63556c3f51ec6743` (2026-11-06) to
`bf3bdd0eaefe39289bf9620594f254c7f68897f5` (2026-11-13), fixed in M0. Upstream
CI passed on it. It includes #9418, which repaired upstream `main` after
`2636e986a`. It does not move after M0.

## Release thesis

Block released **Buzz 1.0** as a new desktop app in
[`block/buzz-app`](https://github.com/block/buzz-app). It is in beta and has
preview builds only. `block/buzz` is now "Buzz 0.X": it is still supported and
still hosts the relay, the CLI, mobile and the protocol crates bzz uses. Both
apps talk to the same relays.

bzz's pin is only 82 upstream commits old. The crates bzz imports changed
little: 117 lines, with no toolchain, dependency or NIP document change. The
work is therefore not catching up with the protocol, but:

1. **Fixing a correctness gap the new relay makes visible.** bzz downloads
   message edits (kind `40003`) but never applies them. Since #9226 an edit
   also replaces the message's attachment set, and media read authorization
   follows the latest edit. bzz shows stale text and can show attachments the
   relay no longer serves.
2. **Working with Buzz 1.0 as a credential provider.** Buzz 1.0 serves the same
   local credential provider contract (version 1, same advertisement directory
   `~/.buzz-foundation/credential-providers/`) and supports `pair`. It does not
   prompt for sensitive kinds. It denies them, and denies every kind outside
   its table. With a Buzz 1.0 identity, bzz would currently fail late on
   deletes, joins, leaves, huddle lifecycle (`48100`–`48106`), reports
   (`1984`) and profile edits.
3. **Following the cross-client contracts Buzz 1.0 publishes with portable
   fixtures:** contextual identity names (v1) and mention rules (v3). They need
   no wire changes, and the fixtures make conformance testable.
4. **Recognizing what Buzz 1.0 and mobile create:** Solo chats (private
   `stream` channels labeled `t=buzz.solo`) and synced sidebar sections and
   sort (kind `30078`, `d=channel-sections` / `channel-sort`).

The explicit human send boundary, key custody and every v0.13 trust boundary
stay as they are.

## Cross-cutting rules

v0.13's seven rules still apply: capability first, proof before trust, inert
untrusted text, privacy, admission budget, no silent republish, and one exit
gate per milestone. Two rules are added:

8. **Contracts by fixture.** Where upstream ships portable fixtures, bzz
   vendors them at a pinned revision and runs them as tests. A fixture bzz
   deliberately does not follow is listed with its reason.
9. **Provider-aware actions.** An action that needs a kind the identity's
   signer cannot sign is refused before the user composes it, with a reason.
   It never fails after the user commits to it.

## M1 — Message edits

The behavior to match is `docs/effective-message-edits.md`.

1. **Apply edits.** For kinds 9, 40002, 40008, 45001 and 45003, select the
   latest live `40003` in the same channel that targets the live original:
   - the target is the first valid 64-hex `e` tag in signed order, compared
     case-insensitively;
   - the greatest `(created_at, id)` wins;
   - a deleted edit drops out.
2. **Show it.** Show the edited text with an "edited" marker after the body,
   as mobile does since #8863. The thread summary and search show the
   effective text.
3. **Attachments.** The latest edit's `imeta` set replaces the original's. An
   empty set means no attachments and never falls back to the original. Media
   fetches use only effective references.
4. **Edit own messages** (D1): a free key (chosen in `ui/keymap.rs`) on a
   selected own message opens the composer
   with its text and attachments, and publishes with `build_edit_with_media`
   through the outbox and the human send boundary.
   - Before signing, bzz reads the `effective_edit` v1 envelope, checks its
     target and channel, and stamps the edit after the observed head.
   - On a relay without the lookup, edits fail closed with a clear notice, as
     the upstream CLI does.
5. **Store.** A migration indexes edits by target. Startup integrity and the
   upgrade test cover it.

**Exit:** fixtures cover casing, ties, deletion, an empty `imeta`, a
cross-channel edit and a non-governed kind. Against the pinned relay, an
edited message with a removed attachment no longer shows it, and an edit from
bzz keeps the attachments.

## M2 — Buzz 1.0 as identity provider

1. **Pairing proof.** Pair bzz with the Buzz 1.0 Linux preview (AppImage) in
   its own sandbox, using a generated identity and the harness relay.
   - The sandbox is a copy of the host's `~/.local/bin/buzz-firejail` with
     `--noprofile`, safe rendering and the GStreamer plugin blacklist. It uses
     a disposable private `HOME` under `runs/experiments/` and a private D-Bus
     session with its own keyring.
   - It has no Codex authentication view.
   - The host's Buzz 0.X home and Secret Service are never reachable.
   - The AppImage is checked against the release's `SHA256SUMS`.

   Record what works:
   - `describe`;
   - `sign_event` for messages and reactions;
   - `nip44`;
   - `federated_identity`;
   - AUTH, NIP-98 and Blossom proofs.
2. **Signer capabilities.** Add a capability table to the signer:
   - a local key signs everything;
   - a provider identity signs the contract's ordinary kinds and its three
     auth-proof kinds.

   Sensitive kinds may answer `approval_required` or `denied`. Unknown kinds
   are denied.
3. **Refuse early.** Delete, join, leave, huddle start, end and leave, report,
   profile and status edits, and channel creation each check the capability
   first. When it is missing, the UI says "Buzz Desktop does not let other
   apps do this; use Buzz", and the composer or dialog does not open.
   - `approval_required` keeps the draft and says that Buzz is waiting for
     approval.
4. **Ownership proof.** The socket ownership check retries a missing proof on
   the same connection within the existing 5 s limit (#9270). A wrong UID still
   fails at once.
5. **Docs.** Document Buzz 1.0 alongside Buzz Desktop 0.X: what works, and what
   needs the app itself.

**Exit:**
- the fake provider (T5) gains the Buzz 1.0 policy table;
- every refused action is typed and tested;
- a real pairing with the Buzz 1.0 preview is recorded with its revision.

## M3 — Identity names and mention rules

1. **Vendor the fixtures.** Vendor `identity-names.fixtures.json` and
   `mention-rules.fixtures.json` under `tests/fixtures/buzz-app/` with their
   source revision and licence (Apache-2.0).
2. **Contextual identity names v1.** Distinct labels within one view:
   - humans before agents;
   - the viewer's identities first;
   - owner names before key suffixes.

   Labels are presentation only. Keys, mentions and tags never change.
3. **Mention rules v3.**
   - Choice set, matching (including exact hex and npub), ranking, and
     completion by Space or closing punctuation.
   - Archived members are excluded.
   - Mentioning someone outside the channel asks before sending.
   - Tags are `p` plus the two-field `mention` tag.
4. **Conformance.** A conformance test runs every fixture case. Cases bzz
   cannot apply in a terminal, such as avatars, are listed in the test with
   their reason.

**Exit:** all applicable fixture cases pass, and T9 covers the mention picker
with same-named people and agents.

## M4 — Solo chats and sidebar sections

1. **Solo.** Recognize `t=buzz.solo` private `stream` channels and show them
   in their own sidebar group, under the relay-derived creator. Create a Solo
   chat (D3) with the same kind `9007` command Buzz 1.0 emits
   (`channel_type=stream`, `visibility=private`, `t=buzz.solo`), checked
   against upstream's `test-fixtures/solo-creation.json`. The relay derives the
   creator; bzz never authors `P`. Adding agents uses the existing membership
   commands.
2. **Sections and sort.** Read the user's `30078` `channel-sections` and
   `channel-sort` documents, which hold per-field last-writer-wins registers.
   Group the sidebar to match Buzz.
   - Unknown `meta.v`, unknown keys and anything over the caps
     (100 sections, 1,000 assignments, 104 sort groups) leave bzz's own
     grouping in place, with no notice.
   - Writing (D3): create, rename, reorder and delete sections, assign
     channels and choose a sort mode. bzz writes as `buzz-cli` does:
     - stamp registers with its own device id;
     - never republish unknown keys;
     - treat `duplicate:` on a resend as success (#9202);
     - publish through the outbox, with a newer head reconciled instead of
       overwritten.

**Exit:** fixtures from the upstream CLI tests decode and re-encode
identically, and the sidebar groups and orders the same as Buzz on the pinned
relay. A section edited in bzz appears in `buzz sidebar sections list`, and one
edited with the CLI appears in bzz.

## M5 — Small parity

1. **Agents in DMs.** Map the relay's DM refusal for agents (#9371) to a typed
   broker error (`forbidden`). The broker already requires the `bot` role,
   which DMs do not grant, so this is a test plus an error mapping.
2. **User-Agent.** Send `bzz/<version>` on the relay and huddle-audio
   WebSocket upgrades. HTTP clients already do. Without it, the audio socket
   would now announce `buzz-audio-client/<version>`.
3. **Single-community relays.** A 404 on the upgrade or NIP-11 reads as "this
   relay serves another community", not as a network error.
4. **Filters.** No request is sent with an empty `ids`, `authors`, `#h`, `#e`
   or `#a` set. A unit test enumerates every builder.
5. **Search paging** (D5): "load older results" in the search view, with the
   `--before`/`--before-id` cursor semantics of #9382.

**Exit:** each item has its red/green test, and the harness shows the agent DM
refusal and the User-Agent.

## Explicit non-goals

v0.14.0 does not:

- run Buzz 1.0 plugins or agents, or implement NIP-PS;
- replace Buzz 1.0 for the actions its provider refuses;
- implement operator, workflow or mobile features;
- change any v0.13 non-goal.

## Definition of done

1. Every milestone's exit gate passes on the fixed baseline.
2. Edits show as Buzz shows them, including attachments.
3. bzz works with a Buzz 1.0 identity for everything its provider allows, and
   says clearly what it does not allow.
4. Names and mentions pass the upstream fixtures.
5. Solo chats and sections appear as in Buzz.
6. Every row of "Testing v0.14.0" is proven in `docs/validation-v0.14.0.md`,
   or marked pending with the reason.
