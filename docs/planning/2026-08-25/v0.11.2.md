# bzz v0.11.2 — Discoverable thread summaries

**Status:** Implemented and locally validated 2026-08-25; publication pending

**Protocol baseline:** unchanged `block/buzz`
`9f55bf67456be10ff7c8238bf0d9e12e582848f6`

## Release thesis

v0.11.2 is a bounded presentation correction: a top-level message with replies
must visibly identify itself as a thread before the context pane is opened.
Today bzz hides replies from the main timeline correctly, but gives the root no
reply count or activity hint. A user therefore cannot distinguish a quiet
message from the head of a busy thread.

The release adds a compact, text-first summary below each root with replies:

```text
      ↳ 13 replies · last reply 6 minutes ago
```

The existing explicit `Enter` / contextual-action flow continues to open the
thread. There is no thread-tree redesign, protocol-baseline bump, schema
migration, or change to publication, read-state, Inbox, agent, credential, or
privacy boundaries.

## Field evidence

The production `#temp-20260825` journey exposed the defect:

- with the context pane closed, roots such as `@Bumble estas?` look identical to
  messages without replies;
- opening context reveals the root plus a substantial reply conversation;
- the current context title says `12 messages`, counting the root itself and
  obscuring the more useful `11 replies` distinction; and
- Buzz Desktop presents the same roots with participant faces, a descendant
  count, and relative last-reply activity such as
  `13 replies · last reply 6 minutes ago`.

## Reference review

### Concord

Reviewed `chojs23/concord` at
`0bac5125ddbecb34b357c40d0348bf660c6099ba`.

Concord's closest pattern is its Discord thread card. It keeps thread metadata
outside the opened conversation and renders textual, width-aware metadata such
as comment count, new-message count, and relative activity. This is a useful
presentation principle, but it is not a direct model for bzz: Discord threads
are separate channels and Concord primarily renders a card for a
`THREAD_CREATED` system message. Copying that larger card would overstate the
scope and consume too much vertical space in bzz's stream timeline.

### Buzz Desktop

Reviewed the pinned compatibility source at
`9f55bf67456be10ff7c8238bf0d9e12e582848f6` and current source at
`7a1b7d8e09f96c10b6617a66bb8589e9984ffb3c`.

Buzz's `MessageThreadSummaryRow` is the appropriate behavioral reference:

- it renders directly under the thread head;
- it uses total descendants, not only direct children;
- it pluralizes `reply` / `replies`;
- it shows relative last-reply activity;
- it keeps unread count separate from total count; and
- it opens the exact thread from the summary.

Buzz combines locally assembled descendants with relay-signed kind `39005`
thread summaries. The pinned relay already defines kind `39005` as synthesized,
relay-signed, non-persistent metadata carrying `reply_count`,
`descendant_count`, `last_reply_at`, and participant pubkeys.

## Decisions

### Follow Buzz's compact row, not Concord's full card

bzz will use one text-first metadata row below the root. The stable `↳` marker,
count, and wording carry meaning in monochrome terminals; color is only
supplemental. Participant avatars are not required for v0.11.2 because image
placements on every thread head would add decoding, flicker, width, and scroll
complexity without solving discoverability.

### Count descendants

The visible number is the count of all non-deleted descendants whose exact
stored `root_event_id` is the selected top-level event. A nested reply counts
once. The root itself does not count.

Only authored message kinds `9` and `40002` count. Reactions, kind `40099`
system rows, deletion records, summaries, and other auxiliary events do not.
Pending, unknown, and rejected local outbox events do not inflate the count;
accepted or relay-observed events do.

### Durable local truth plus optional signed live overlay

The restart/backfill source is the existing verified local event archive. bzz
already backfills reply-inclusive channel content and stores exact root/parent
coordinates. For the at-most-500 retained timeline roots, one bounded store
query derives:

- descendant count; and
- latest non-deleted descendant timestamp.

This summary therefore matches the exact conversation the context pane can
open, survives restart without new durable state, and updates after ordinary
reply/deletion ingestion.

For live parity with Buzz, the selected channel subscription may additionally
accept kind `39005`, but only as transient metadata:

1. verify the Nostr signature;
2. require the configured pinned relay signer;
3. require exact matching lowercase 64-character `e` and `d` root tags;
4. require the exact selected `h` channel UUID;
5. parse bounded non-negative counts, timestamp, and participant fields;
6. require `reply_count <= descendant_count` and internally consistent zero
   and timestamp states;
7. retain it only when the root is one of the currently retained top-level
   messages; and
8. keep only the newest deterministic `(created_at, event_id)` summary per root.

Kind `39005` is never inserted into `events`, search, Inbox, unread state,
diagnostics content, or telemetry. The in-memory map is bounded by the visible
root window and is cleared on community/channel replacement. Malformed,
wrong-signer, wrong-channel, unknown-root, or oversized summaries are ignored
for presentation and local derivation remains available.

As in Buzz, the displayed local/live merge uses the greater current descendant
count and latest reply timestamp. This avoids a stale overlay temporarily
hiding a just-ingested reply. After a threaded deletion is applied, local and
relay-derived counts can both decrease. A signed summary is presentation
metadata, not authorship, membership, read, or send authority.

### No full channel-window migration

v0.11.2 does not adopt kind `39006`, top-level cursor pagination, Buzz's entire
channel-window store, forum cards, or relay participant facepiles. Those are
separate architectural changes. Existing bzz history/backfill and context
navigation remain intact.

### Relative activity is presentation-only

Use the same expanded ladder users see in Buzz:

- `just now` below one minute;
- `1 minute ago` / `N minutes ago`;
- `1 hour ago` / `N hours ago`;
- `1 day ago` / `N days ago`; and
- `on YYYY-MM-DD` after seven days, matching bzz's existing ISO date style.

Future timestamps clamp to `just now`. Relative formatting performs no writes
and must not itself trigger refresh, redraw, read acknowledgement, diagnostics,
or network work.

### Context title reports replies

When context is open, its title reports descendants rather than counting the
root as an ordinary message:

```text
context · 11 replies · q close
```

Use `1 reply`, `N replies`, or `no replies`. The root remains the first visible
context row. This is a wording/presentation correction only.

## Workstream A — Bounded summary projection

1. Add a small presentation model keyed by exact root event ID with
   `descendant_count` and `last_reply_at`.
2. Derive local summaries only for the currently retained main-timeline roots
   (maximum 500), using the existing `(community_id, root_event_id, created_at,
   event_id)` index and strict community/channel predicates.
3. Exclude deleted and non-delivered local descendants as defined above.
4. Refresh the map through the existing cache-dirty path after reply,
   deletion, backfill, channel switch, reconnect, and outbox-state changes.
5. Do not add a migration, summary table, periodic polling loop, or per-frame
   SQLite query.

## Workstream B — Strict live kind `39005` handling

1. Add kind `39005` only to the bounded selected-channel subscription, not the
   global stream.
2. Parse and validate it before the general durable `apply_event` path.
3. Enforce signature, pinned signer, exact root/channel tags, payload bounds,
   and deterministic replacement.
4. Merge it into the current visible-root summaries without storing the event.
5. Mark only the in-memory presentation cache dirty; do not rebuild Inbox,
   search, profiles, agents, or read state.
6. Keep local projection as the restart and malformed-overlay fallback.

## Workstream C — Timeline and context presentation

1. Render the summary after the root body/attachments and before reactions.
2. Indent it to the existing message text gutter and use `↳` plus explicit
   wording so monochrome and no-image terminals remain understandable.
3. Render no row and consume no vertical space when the descendant count is
   zero.
4. Keep the whole message block as the existing mouse/selection target; the
   summary introduces no hidden click-only action.
5. Preserve `Enter`, contextual actions, and `q` behavior.
6. Update the context title to report replies, excluding the root.
7. Keep summaries out of copied message content, search snippets, diagnostics,
   and accessibility-independent color semantics.

## Correctness and resource invariants

- No thread summary may cross community or channel boundaries.
- A descendant is counted once even when it replies to another reply.
- Same-second events use event ID only for deterministic ordering; count and
  latest timestamp remain stable.
- Deleted replies disappear from count and latest-time calculation.
- Deleting the newest reply moves `last reply` to the next newest remaining
  descendant or removes the row at zero.
- A deleted root may retain a summary while valid descendants remain, so its
  conversation is still discoverable.
- Opening/closing context, rendering, and relative-time changes perform no
  SQLite writes or network requests.
- Summary derivation is bounded to the retained root window and uses one store
  call per cache hydration, never one call per rendered row.
- Live overlay state is bounded, transient, content-free beyond typed counts and
  timestamps, and absent from OTel and private diagnostics.
- Existing thread publication coordinates, acknowledgement-aware drafts,
  unread/read contexts, Inbox projection, and human-send boundaries do not
  change.

## Validation matrix

### Store and protocol

- zero, one, and many descendants;
- nested descendants counted once by root;
- community/channel isolation;
- kind `9` and `40002` included; auxiliary/system kinds excluded;
- deleted newest and deleted final reply recomputation;
- pending, unknown, rejected, delivered, and relay-observed outbox states;
- bounded 500-root query and large-count conversion;
- valid signed `39005` accepted transiently;
- wrong signer/signature/channel/root, mismatched `e`/`d`, malformed JSON,
  inconsistent counts, invalid pubkeys, and oversized content rejected;
- a newer summary may count down; an older duplicate cannot overwrite it; and
- no `39005` row appears in SQLite, Inbox, search, or diagnostics.

### Rendering and interaction

- no-reply roots retain the current height;
- exact snapshots for `1 reply` and `13 replies`;
- relative minute/hour/day/date boundaries;
- selected/copy-selected styles remain aligned;
- summary wrapping/truncation remains readable at narrow widths;
- avatars, attachments, reactions, deletion state, and agent markers keep their
  existing alignment;
- clicking the summary area selects the root and `Enter` opens exact context;
- context title excludes the root from the reply count; and
- copied text contains authored content only, not synthesized summary wording.

### End to end

- deterministic fake-relay journey: root, direct reply, nested reply, deletion,
  restart, and backfill;
- pinned Buzz relay integration confirms kind `39005` signer and payload shape;
- Herdr release-binary acceptance captures closed timeline, open context, narrow
  fallback, mouse selection, and terminal restoration;
- Linux, Windows, Intel macOS, and Apple Silicon CI; and
- a quiet idle observation confirms no polling, SQLite churn, or redraw loop.

## Explicit non-goals

v0.11.2 does not add:

- inline expanded reply trees in the main timeline;
- participant avatar facepiles;
- per-thread unread badges or changes to read acknowledgement;
- thread following, muting, collapsing, sorting, or notification policy;
- forums or Concord-style full thread cards;
- kind `39006` or a full Buzz channel-window client;
- new thread publication semantics or implicit replies;
- periodic summary polling;
- a database migration or durable derived summary table; or
- any change to remote-agent verification, hosting, runtime control, keys, or
  autonomous publication.

## Release gates

v0.11.2 is ready only when:

1. every visible root with locally known or valid signed-summary descendants has
   an explicit textual thread row;
2. zero-reply messages remain visually unchanged;
3. counts and latest activity update correctly on reply, nested reply, deletion,
   reconnect, and restart;
4. the context title reports replies rather than root-plus-reply messages;
5. malformed or unauthorized `39005` input cannot affect presentation;
6. summary metadata cannot affect Inbox, unread, search, copy, diagnostics,
   OTel, or publication authority;
7. rendering and store work remain bounded with no idle churn; and
8. local, pinned-relay, Herdr, cross-platform, dependency, release, and artifact
   gates pass.
