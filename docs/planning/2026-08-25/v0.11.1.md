# bzz v0.11.1 — Agent identity projection and conversation presentation

**Status:** Proposed 2026-08-25

**Protocol baseline:** unchanged `block/buzz`
`9f55bf67456be10ff7c8238bf0d9e12e582848f6`

## Release thesis

v0.11.1 is a client-only correctness patch for defects exposed by a real
conversation with the existing Fizz managed agent. It repairs historical bot
role projection, recognizes verified agents in bounded DMs without requiring a
relay change, presents agent/owner identity consistently in conversations, and
stops rendering relay-authored system JSON as an ordinary user message.

It does not add local hosting, runtime control, agent credentials, manual trust
buttons, or autonomous publication. The human-send and acknowledgement-aware
draft boundaries remain unchanged.

## Field evidence

The 2026-08-25 Fizz journey established all of the following:

1. A bzz-authored mention in a DM carried the exact Fizz `p` tag.
2. Fizz returned a signed kind `9` threaded reply; bzz verified it, resolved the
   Fizz profile, rendered its avatar, and preserved exact root/reply
   coordinates.
3. Mentions authored from bzz, Buzz Desktop, and Android in `#eng` had the same
   exact `h` and `p` tags. The first unanswered bzz mention was therefore not a
   wire-format difference; runtime availability is external to bzz.
4. Buzz Desktop rendered Fizz as an agent and `managed by you`; bzz rendered the
   same signed identity as an ordinary profile.
5. The latest cached relay-signed kind `39002` snapshot for `#eng` marks Fizz
   with the exact `bot` role, but the upgraded bzz `memberships` projection
   still records `member`.
6. v0.11.0 treats an already-stored event ID as an ingestion no-op, so a current
   historical `39002` snapshot is not replayed after the role-aware projection
   code is installed. The agent refresh consequently reports zero candidates.
7. Buzz DMs deliberately store every participant with operational role
   `member`; requiring a destination-DM `bot` role makes public remote
   recognition impossible even when NIP-OA and the agent declaration validate.
8. Kind `40099` `dm_created` is relay-authored control data, but bzz currently
   displays its raw JSON and relay pubkey as an ordinary message.

These observations identify bzz projection and presentation defects. They do
not justify a Buzz relay change.

## User-visible outcome

After upgrading an existing v0.11.0 profile, the user can:

- reopen bzz without clearing SQLite or rebuilding their identity;
- have historical exact `bot` roles repaired from already-verified signed
  membership snapshots;
- see Fizz and equivalent identities automatically verified without approving
  them one by one;
- see a guaranteed textual agent marker in channel, DM, thread, mention, and
  directory presentation;
- see `managed by you` only when valid NIP-OA proves the active identity is the
  owner;
- see another verified owner's sanitized profile label or abbreviated pubkey;
- see the selected agent's existing public profile avatar where the terminal
  and avatar policy support it;
- mention an owner-controlled verified agent in an exact DM even though Buzz
  stores DM participants with operational role `member`;
- continue to review and explicitly send every message; and
- see a human-readable DM introduction instead of raw `dm_created` JSON.

An unanswered mention remains an external runtime outcome. The UI must not call
an agent online, ready, healthy, or available merely because its profile,
ownership, declaration, role, or an older reply validates.

## Decisions

### No manual verification

There is no per-agent trust list, approval prompt, fingerprint acceptance, or
`trust Fizz` action. Verification is deterministic and automatic from signed
public records. `bzz agents refresh` and the TUI refresh key only force that
process; they do not change trust.

### No relay or Buzz Desktop change

v0.11.1 changes only bzz. It does not require:

- a new relay kind, endpoint, role, migration, or deployment;
- reading Buzz Desktop's Tauri commands, managed-agent JSON, keyring, process
  receipts, runtime state, or logs; or
- changing the pinned Buzz revision.

### Separate identity, authority, and activity

- A valid profile supplies a name and avatar, not agent authority.
- A verified NIP-OA relationship supplies the owner.
- A valid agent-signed kind `10100` declaration supplies agent intent.
- Relay-signed channel membership bounds where a remote identity is relevant.
- A signed reply proves that identity authored that reply; it does not prove a
  model/runtime is currently ready and does not replace NIP-OA or policy.

### Channel and DM candidate rules

For non-DM channels, the v0.11.0 rule remains unchanged: the destination must
carry a current relay-signed exact `bot` membership for the agent.

For a DM only, the candidate and send-time rules are:

1. the channel is positively known as `dm` (unknown channel kinds still fail as
   DM for policy evaluation);
2. the signed current membership contains 2–9 unique valid participants;
3. the candidate is an exact current participant;
4. the candidate has a valid signed kind `0` NIP-OA profile;
5. the candidate has a valid signed kind `10100` declaration;
6. the NIP-OA owner is exactly the active human identity;
7. any required owner-signed kind `30177` policy is valid and usable;
8. send-time exact refresh and revalidation succeed; and
9. the ordinary human send action is still required.

A display name, avatar, visible `@Fizz`, reply, `p` tag, stale cache record, or
profile ownership claim alone never enables the agent marker or invocation.
This DM exception is bounded by relay-authenticated membership and owner
equality; it is not a global profile scan or general removal of the bot-role
requirement.

## Workstream A — Historical membership projection repair

Add migration `0008_reproject_membership_roles.sql` (or an equivalently
transactional Rust migration) that:

1. considers only existing `memberships` rows and their exact
   `source_event_id`;
2. reads only the already-stored, signature-verified, community-scoped kind
   `39002` source event;
3. reproduces the current parser exactly: role is `bot` only for an exact
   four-field `p` tag whose fourth value is lowercase `bot`; every other role
   remains the non-authoritative `member` class used by bzz;
4. validates pubkey, channel, relay signer, participant uniqueness, and 10,000
   member bounds before changing projection state;
5. updates only rows whose derived role differs;
6. leaves events, channels, messages, drafts, outbox, read state, Inbox, media,
   profiles, diagnostics, and credentials untouched; and
7. reconciles the remote-agent projection once after repair.

Fresh profiles and upgraded v0.10/v0.11 profiles must converge to identical
membership and agent projections.

Duplicate current `39002` ingestion must also repair a missing or inconsistent
current membership projection without re-inserting the event. When the
projection already matches, it remains a true no-op: no SQLite write, Inbox
rebuild, redraw, diagnostic, or timestamp mutation.

## Workstream B — Bounded DM agent discovery and revalidation

Extend agent discovery with a second bounded candidate source consisting only
of current participants in joined, visible DMs. Apply the existing global cap
and exact-author batching; do not query arbitrary profile authors.

The refresh order is:

1. current relay-signed membership;
2. exact-author kind `10100` declaration for bounded candidates;
3. exact-author kind `0` profile;
4. NIP-OA owner verification;
5. exact `(owner, d=agent)` kind `30177` policy query; and
6. community-isolated projection reconciliation.

Send-time revalidation must distinguish destination types:

- **channel:** exact current `bot` role in that channel;
- **DM:** exact current participant plus verified owner equal to the active
  identity and valid public records/policy.

Removing the participant, replacing ownership, deleting/deactivating the
public declaration, invalidating policy, switching identity/community,
locking, or losing refresh certainty must preserve the exact draft and refuse
to sign/send through the agent path. There is no implicit retry.

## Workstream C — Agent-aware conversation presentation

Introduce a presentation-only, community-scoped map keyed by lowercase agent
pubkey. It is derived from verified projections and contains only the fields
needed by rendering: verification freshness, owner relationship, sanitized
agent label, sanitized owner label/abbreviation, and public avatar reference.
It confers no send authority.

Required surfaces:

- timeline author row;
- context/thread author row;
- selected channel/DM header;
- textual channel/DM sidebar row;
- ordinary `@` completion;
- `:agents` list/detail; and
- Inbox/search author presentation where an author row already exists.

Rendering rules:

- verified current agent: `◆ Fizz`;
- verified owner equals active identity: `managed by you`;
- verified different owner: `owned by <sanitized label or abbreviated key>`;
- stale/incomplete verification: no solid verified marker and no asserted
  owner relationship;
- normal profile: unchanged human presentation.

Color is supplemental only. `◆`, wording, and accessible ordering must carry
the distinction in monochrome terminals.

The selected DM/header and selected `:agents` detail may reuse the existing
bounded avatar pipeline. The sidebar's release requirement is the stable
textual `◆` marker, not dozens of image-protocol placements; this avoids
flicker, scroll corruption, and excessive decoding in narrow terminals.

No remote avatar, name, capability, or owner text may become a path, command,
URL-opening action, environment value, log field, diagnostic field, or OTel
attribute.

## Workstream D — Typed system-event presentation

Keep signed kind `40099` records in the event archive, but stop treating them
as ordinary authored messages.

Add a bounded parser for a small reviewed allowlist beginning with:

- `dm_created`;
- `channel_created`;
- `member_joined`;
- `member_left`;
- `member_removed`;
- `channel_archived`;
- `channel_unarchived`; and
- `message_deleted`.

For `dm_created`, resolve exact participants through already-cached profiles and
render a muted, non-author row such as `Direct message started with Fizz`.
Never display the relay pubkey as the author. Missing profiles use abbreviated
pubkeys and may trigger the existing bounded profile hydration path.

Malformed, oversized, unknown, or unsupported system payloads remain stored but
render only a content-free `Unsupported system event` placeholder, or are
omitted where the containing view already provides equivalent context. Raw JSON
is never printed into the timeline.

System events must not inflate human-message counts, unread state, mention
notifications, search results, or agent activity/readiness. Existing deletion
and moderation semantics remain authoritative.

## Workstream E — Refresh and resource behavior

Agent repair and discovery must not reintroduce persistent CPU, SQLite, redraw,
or network churn.

- Startup/reconnect, relevant membership notifications, explicit refresh, and
  send-time exact revalidation are authoritative triggers.
- A periodic directory check must not rewrite unchanged projections or emit a
  redraw.
- Evaluate removing the unconditional five-minute full agent phase when the
  authenticated live subscription is healthy; if a safety refresh remains, it
  must be coalesced, jittered, single-flight, and documented.
- No-change refresh diagnostics are bounded typed outcomes and remain excluded
  from OTel; avoid a journal write on every idle timer tick.
- Candidate, page, concurrency, payload, profile, capability, and queue bounds
  remain explicit.
- Saturated relay traffic cannot delay terminal input, attachment completion,
  shutdown, or acknowledged outbox reconciliation.

Acceptance requires an idle 15-minute observation with no growing SQLite/WAL,
no repeated redraw, no hot loop, bounded journal behavior, and explainable
network requests only.

## Data and compatibility

Expected schema version: 8.

Migration 0008 is reconstructive and idempotent. It changes no Buzz wire record
and publishes nothing. Downgrading to v0.11.0 leaves extra schema state
unsupported; normal release documentation must recommend backup rather than
claiming downgrade compatibility.

No configuration option, agent key, runtime file, process, credential, or
manual trust database is added. Existing `[[local_agents]]` retirement remains
unchanged.

## Security and privacy invariants

1. Human and agent private keys remain separate; bzz stores only the human key.
2. bzz never starts, stops, wakes, configures, observes, or claims readiness for
   Fizz or another runtime.
3. Agent selection never sends automatically.
4. Exact lowercase 64-character pubkeys and deduplicated structured `p` tags
   remain mandatory.
5. Visible `@name` text is never inferred into a tag at send time.
6. DM recognition requires exact participant membership and owner equality; a
   general channel still requires exact `bot` role.
7. Owner wording appears only after NIP-OA cryptographic verification.
8. Signed replies are ordinary remote messages, not ownership or readiness
   evidence.
9. Agent diagnostics/OTel continue to exclude content, names, pubkeys, owner
   pubkeys, event/channel/community IDs, relay URLs, raw tags, and avatars.
10. No NIP-AE memory, NIP-AO observer/control, NIP-PMA private state, or usage
    events are subscribed to, decrypted, archived, or displayed.

## Deterministic regression matrix

### Migration and projection

- v0.10/v0.11 fixture with cached `39002 bot` and projected `member` repairs to
  `bot` exactly once;
- malformed, forged-relay, wrong-community, duplicate-pubkey, oversized, and
  non-current snapshots cannot repair authority;
- fresh and upgraded databases converge byte-for-byte for authoritative role
  rows;
- repeated duplicate current snapshot is a no-op after repair;
- historical repair does not dirty Inbox, alter outbox/drafts, or change event
  bytes;
- membership removal still removes invocation authority.

### DM verification

- exact 2-party and bounded group-DM participant with NIP-OA, declaration,
  owner policy, and active-owner identity verifies;
- a non-owner remains ineligible even under `anyone` or allowlist policy;
- missing/invalid declaration, wrong owner, owner conflict, wrong policy signer
  or coordinate, stale record, malformed participant, and removal fail closed;
- a reply without declaration/ownership never upgrades a human profile into an
  agent;
- non-DM destinations continue to require exact `bot` membership;
- send-time failure preserves the exact draft and mention metadata.

### Presentation

- Fizz-like verified author renders avatar, `◆`, name, and `managed by you` in
  wide and narrow thread/context views;
- different owner resolves safely with fallback abbreviation;
- stale/unverified identities lose asserted marker/owner wording;
- profile avatar failure falls back deterministically without layout shift;
- sidebar remains stable under scroll, resize, community switch, lock, and
  image-capable/image-incapable terminals;
- semantic mouse targets remain aligned.

### System events

- `dm_created` never renders raw JSON or the relay as a user;
- known allowlisted types produce sanitized semantic rows;
- malformed/unknown/oversized payloads cannot panic or leak raw content;
- system rows do not count as unread user messages or search documents;
- relay signer and community isolation remain enforced.

### End-to-end interoperability

The pinned fake/real relay journey must:

1. seed a pre-v0.11 cached role mismatch;
2. upgrade and repair it without clearing data;
3. verify a disposable owner/agent automatically;
4. render its agent and owner semantics;
5. send one exact human-authored mention from bzz;
6. receive a deterministic agent-signed threaded reply;
7. compare its `h`/`p` coordinates with equivalent Desktop-compatible and
   mobile-compatible fixtures;
8. exercise an owner-controlled DM participant with operational role `member`;
9. prove no local runtime, LLM, ACP, tool, memory, observer, or agent key starts;
   and
10. prove an offline runtime causes no retry, false readiness, or content loss.

Manual acceptance uses only a disposable E2E channel/identity. Fizz or another
real agent may be observed only with generated text and no production/private
content.

## Explicit non-goals

- No Buzz relay change or deployment.
- No Buzz Desktop private/local integration.
- No agent creation, key import, hosting, ACP process, provider configuration,
  tool permission, memory, observer control, autonomous publishing, or runtime
  wake/retry.
- No inference from names, avatars, visible mentions, replies, or language-model
  behavior.
- No general relaxation of exact bot-role authority outside DMs.
- No claim that a reply proves future readiness.
- No sidebar gallery of many image-protocol avatars; selected/header/detail
  avatar reuse and textual identity are sufficient for this patch.
